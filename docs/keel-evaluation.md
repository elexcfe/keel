# Keel 评测方案

评测围绕两个产品目标：**提高正确修复的交付率；减少人理解、审核和纠正交付所需的工作。** 最近优先验证“复现评审回放原型”，判断独立评审 Agent 是否能发现复现与断言中的实际问题，再决定是否接入自动反馈。下一项任务的范围、步骤与验收见[复现评审回放计划](../plans/reproduction-review-replay.md)。

当前已有 [Actual 修复闭环记录](../plans/repair-loop.md)：两条已声明路径在外层验收反馈后完成修复并独立复验。它证明有限范围内的可行性，不是首次交付通过或无人干预的闭环，也没有证明 Keel 相比直接使用 Pi 提高了成功率、节约了成本或审核时间。现版修复入口仍要求经过外层审核的复现参考，评测不能悄悄补上这个关口再宣称自主完成。仓库计划提供结果摘要，本机原始产物的复核条件单列，不将忽略目录描述为 GitHub 已托管证据。

本方案定义要证明什么，不代表已有成绩，也不自动授权模型调用、人工受试测量或付费实验。当前仅更新文档和后续计划；原型实现、评测任务集、重复次数和总预算在实际执行前明确。已完成的复现、报告交付或进程清理验证不能算完整修复成功；历史记录不够支持新口径时标为“无法按新口径判定”，不回填成功。已有 [Pi 会话拆分实验](pi-session-experiment.md) 比较的是 single/split，不是基础 Pi 与 Pi＋Keel 的增益，也不是与主流 Agent 的比较。

## 1. 最近优先：复现评审回放

### 回放要回答的问题

回放只读取冻结的原始 Issue、复现方案、断言、运行记录和相关证据，判断它们是否足以支持“已经复现原问题”。例如，Issue 是修改参数后滚动位置重置，断言却只检查参数值变化；或报告中的异常时间段与视频不符。评审应指出具体缺口并引用证据，不能只给一个通过分数。

原型阶段不修改 Pi 产物，不重新运行场景或修复任务，不触发退回重做，不授予正式准入或交付状态。结构、版本和证据完整性等现有程序能检查的问题先单列；模型负责判断目标行为是否被覆盖、证据是否支持结论。输出固定为**建议通过、退回、无法判断**，同时保存依据、证据位置及需要补充的内容。材料不足时必须允许无法判断，不能靠猜测补全。

### 材料、标注和泄漏控制

- 优先冻结真实任务在不同交付阶段的材料；保留来源、时间点、源码/场景版本、文件摘要及与原始证据的对应关系。旧外层意见可以帮助评测方发现候选样例，但不能直接当作未经复核的答案。
- 独立标注者按原始 Issue 和证据制定“可通过、应退回、证据不足”的参考判断及理由；分歧先复核，仍不能确定的样例单列，不能默认为通过或悄悄删除。标注理由与参考答案只供评分使用。
- 开发集和留出集按 **Issue** 划分。同一 Issue 的多轮报告、不同场景和合成变体不能分散到两组，避免用已经见过的错误模式证明未见任务能力。留出集在提示和规则冻结后使用；一旦据此调试，就需另设后续留出材料。
- 如增加合成错误样例，在独立派生材料中明确标记构造方法、来源和用途。不得改写 Pi 的原始场景、报告、日志或画面，也不能把合成错误计为真实生产失败。
- 给评审 Agent 的材料包只含本轮需要的输入；独立标注、旧外层结论、修复答案及参考补丁与输入分开存放，不授予读取权限。不能仅在提示里要求“忽略答案”，却仍让它读取完整实验目录。

### 回放指标

先报告各参考类别的样本数、不同 Issue 数、真实/合成来源和完整混淆表，再报告以下指标；分母为零时写“不可计算”，不记为零错误。超时或协议错误作为调用失败保留在全部登记样例中，不能悄悄剔除，也不能等同于有依据的“无法判断”。

| 指标 | 口径与限制 |
| --- | --- |
| 错误放行率 | 在独立标注为“应退回或证据不足”的样例中，模型输出“建议通过”的数量 ÷ 全部此类样例数；两类分别报告，避免证据缺失被掩盖 |
| 通过建议中的错误比例 | 错误放行数 ÷ 全部“建议通过”数；与上一指标同时报告，说明用户收到通过建议后可能遇到的错误 |
| 错误驳回率 | 在标注“可通过”的样例中，模型输出“退回”的数量 ÷ 全部“可通过”样例数；无谓返工不能忽略 |
| 无法判断率、判断覆盖率与调用失败率 | 分别为输出“无法判断”的数量、输出有效通过或退回建议的数量、未取得有效评审的数量 ÷ 全部登记并尝试回放的样例数；按参考类别拆分，不能靠全部拒判或排除失败换取低误放行 |
| 人工核查负担 | 记录核查建议与原始证据所需的实际操作时间、判断正确率、追问与返工；没有真实测量时标为未测，不能由报告长度或模型输出推算 |
| 回放成本 | 记录全部模型调用、程序检查、重试、耗时及人工标注/核查费用；按样例和 Issue 汇总，失败调用也计入 |

评审建议本身不是真值。独立标注与终局判卷不能由同一个工作流评审 Agent 自己完成；若使用 AI 辅助标注，需披露模型和人工复核边界，不能把模型自洽当作准确。已有开发案例用于复现已知失败模式，不能替代留出评估。

初期回放应完整核对样例。后续试点即使两个 Agent 都同意通过，也必须按事先制定的规则抽检，不能只审核分歧或低置信度结果。报告抽样方式、覆盖范围和发现的共同误判，不以少量样例零错误宣称可靠；允许减少人工的质量要求和样本规模须在试点前确定，当前不预设未经验证的阈值。

## 2. 端到端交付率

**端到端交付率 = 在预定预算内、无人工救场且通过独立交付验收的任务次数 ÷ 预先登记且已结束的有效任务次数。**

完整流程从原始 Issue、附件、故障版本源码和相同基础环境开始，到交付代码、验证证据和说明并等待审核结束；不要求自动合并或部署。Issue 本来包含的操作步骤保留，不额外向一组提供复现脚本、断言、根因、后续修复评论或参考补丁。启动前确定时间/费用预算、最大重试次数、所需回归范围和人工参与边界。任务内部的失败与重试不另算多个任务；比较中同一 Bug 的预定独立重复按任务次数计，同时报告不同 Bug 数量，不能靠反复跑一个容易案例增加样本。

主实验运行期间没有临时人工或外层 AI 纠偏；评分标准提前冻结，只能用于运行结束后的独立验收，不能反馈失败项帮助本轮修改。工作流内的评审 Agent 属于被测系统，调用、退回和耗时全部计入；它不能同时担当最终裁判。人工或独立 AI 为实验准备验收标准不等于运行中救场，但准备和判卷成本应另列。

若两组都拿到已经审核的复现材料，测到的仅是修复阶段收益，必须另行命名和报告。当前版本在外层准入处停住时，应记为自主流程未完成，不能自动写入审核通过或排除该任务。带中间审核的协作实验与无人干预实验分开统计；如需改造候选状态或接入自动评审，所得结果属于明确记录的新版本，不能追溯为现版能力。

### 什么算成功交付

所有条件同时满足，才计入分子：

1. 修复前以真实操作或检查观察到目标 Bug，独立验收确认它对应原问题；环境错误、导航超时不能冒充 Bug。
2. Pi 产出修复；修复后同一已确认的场景、断言和数据条件通过。若检查本身需要纠正，重新评审并在修复前版本上建立有效失败记录，保留版本差异，不能放宽断言制造通过。
3. 预先约定的相关回归检查已运行，无本次引入的失败。已有失败单列并有依据；无法分清新旧失败、必需检查未运行时不能计成功。
4. 在预算内交齐可重跑的代码、场景、运行记录及说明；证据、结构化检查和报告一致，说明原因、改动、验证范围与限制。文件齐全、Agent 退出 0 或测试通过，均不能单独判成功。
5. 独立验收者按统一标准核对代码、证据并原样重跑必要检查，确认修复针对目标问题；不能只采信生产产物的 Agent 自评。验收记录另存，不修改原报告或原始证据。

对闪烁、瞬间消失等问题，原始视频清楚证明操作与异常即可作为主要界面证据，不强求截图截中瞬间。Pi 必须说明以视频为主，提供具体轮次的视频链接、异常时间段和应观察的现象；截图说明仍须准确。

### 失败、人工介入与预算

| 情况 | 统计方式 |
| --- | --- |
| 环境准备失败、无可运行检查、超时、超费用、中途放弃、交付部分完成或验收不通过 | 有效任务计入分母，不计分子，保留原因 |
| 预算内自主重试、恢复环境、发现错误后修正 | 可计成功，同时计入该任务总耗时、费用和重试数 |
| 人给出关键定位/补丁、修复脚本或数据、补写报告、救活环境 | 记录人工救场；即使最终通过，也只列为“辅助完成”，不计自主交付分子 |
| 运行中来自人工或系统外 AI 的复现/定位审核及纠偏 | 无人干预主实验不允许；实际发生则记录为辅助完成。带外层审核的协作实验另列流程、反馈范围、次数和人力成本，不混入自主结果；系统内评审 Agent 按上文计入被测系统 |
| 预先约定的权限批准、任务结束后的最终审核 | 保留次数、内容和等待时间；不得借此补充解法或将验收意见回传用于修改本轮产物 |
| 已知的启动前材料准备 | 明确列为输入条件，不能声称由 Agent 自主完成；各组条件一致 |
| 外部执行器故障导致试验本身无效 | 依预先约定规则、独立证据单列；保留该次记录和成本，不能因某组失败而事后排除 |

生产阶段预算计入环境准备、执行与评审模型调用、工具运行、退回重做、重试及收尾；实验终局验收另记耗时与成本，不能拿验收时间继续补产物。人工等待是否暂停执行预算在开始前统一约定，实际端到端墙钟时间仍报告。费用为估算时注明来源与缺项。

汇总必须同时给出成功数/总次数、不同 Bug 数、失败原因、人工救场次数、费用和耗时。每次正确交付成本的分子应包含全部尝试的模型和执行费用、人工审核与持续抽检、失败/返工费用及合理的开发校准维护摊销，分母为独立确认正确的交付数；零成功时不可计算。成本报告分别列出运行费用、持续审核费用、开发校准维护及其摊销假设、仅为实验统一判卷的费用，避免重复计费或把必要人力当作免费。人工时间减少与现金支出变化分别说明，不要用更大预算下的胜出声称效率更高。

## 3. 帮助人理解 Bug 与修改

目标是让审核者更快作出正确判断，不以报告长度、图片数量、关系图复杂度或主观“看起来清楚”作为主要成绩。

在同一任务上，要求不熟悉该任务的审核者回答固定问题：

- 怎样触发 Bug，用户会看到什么异常？
- 原因是什么，哪些是已证实事实，哪些仍是假设？
- 改了哪里、为什么能解决问题，影响范围是什么？
- 哪些检查真正运行并通过，哪些部分未验证，是否还需补充证据？

依据源码、差异和实际执行证据，由独立评审预先制定答案与评分规则。主要记录**完成问题所需时间与回答正确率**；同时保留超时/未答、关键风险误判和查找证据所需的追问。不能仅筛选答对的人计算时间，或因读得更快而忽略正确率下降。满意度只作补充。

先用已有任务材料做小规模可用性观察，发现说明缺口；正式对照再采用以下安排：

- 同一份已冻结的修复与证据，比较基础说明和 Keel 说明，尽量固定信息来源，使差异来自组织与解释方式。若比较的是不同 Agent 的完整交付，注明内容质量也不同，不能把差异全归因于报告形式。
- 隐去工具名称，随机/交叉安排不同任务的材料；避免同一人先看一份答案再看同一 Bug 的另一份。记录参与者经验，平衡任务难度与阅读顺序。
- 预先确定人数、题目、时间上限和可接受的准确率差异；报告人数、分数、时间分布及失败，不预设“20 秒理解”之类未经验证的成绩。

没有实际人员参与测量时，仅能说“交付了有依据的说明”或“通过内容检查”，不能宣称节省了审核时间。自动检查和 AI 评审可帮助检查一致性，不能代替真实人的理解效果。

## 4. 辅助指标与最小记录

保留旧指标，帮助解释交付在哪里失败：

- **验证流程完成率：** 修复前复现、修复后检查、相关回归均实际执行的任务次数占全部已结束有效任务次数的比例。测试运行后失败仍可能满足“流程完成”，不能替代端到端交付率。
- **交付前自动纠错：** 系统发现首次修改仍有问题或引入回归，在无人工救场情况下自行修正，最终目标检查通过且相关回归无新增失败。分别统计已纠正和未纠正；环境恢复另记，不冒充修复纠错。

复用现有任务、会话和场景记录，不为此先建设评测平台。每次至少能追溯：任务/轮次、源码与输入版本、工具/模型及提示配置、预算与实际成本时间、重试、人工介入、原始证据、评审建议、独立验收与失败原因。回放额外记录样例来源、开发/留出分组、参考标注版本和材料读取范围；理解测量开始后才增加匿名参与者、材料版本、题目评分和用时记录。当前未采集的字段标缺失，不推算为零。

## 5. 分阶段验证

| 阶段 | 目的和工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| 1：复现评审回放 | 下一项任务；只读冻结材料，检查模型评审能否发现真实复现与断言问题，保留错误放行、错误驳回和无法判断 | 产出可重复回放入口、开发/留出材料与错误分析；按事先确定的质量要求判断是否值得接入反馈，不以单个成功样例自动推进 |
| 2：有限自动反馈 | 在通过前一阶段判断后，接入评审退回、Pi 重新产出和复验；限定次数与总预算，保留停止和交接出口 | 记录纠正、无谓返工、共同误判与完整成本；评审建议到正式状态的转换规则和独立终局验收已明确。组件有效不能代替闭环有效 |
| 3：原始 Issue 完整对照 | 先比较相同执行模型的基础 Pi 与 Pi＋Keel；评估复现、检查设计、修复、交付和人力负担，再按需要做消融 | 任务集、版本、验收协议、次数和预算明确；披露尚未自动化的关口。样本与差异不足时不宣称收益 |
| 4：Skill／CI 接入 | 有复用需求时，让薄 Skill 引导调用共享工具，CI 复用同一检查；核心检查继续可脱离 Pi 执行 | 接入不会改变结果含义或隐藏成本；与直接使用已有工具的负担比较。不以独立客户端或多框架适配作为前置目标 |

阶段 3 固定执行模型版本、推理设置、起始代码、任务材料、可用依赖、网络、缓存起点与预算。两组获得相同的交付目标和允许工具能力；基础 Pi 可正常分析、自测、修正和使用工具，不要求采用 Keel 的文件格式或流程，也不能刻意削弱。Keel 的流程编排、上下文整理、验收反馈和证据组织是待评测的处理差异，需完整披露；额外评审模型的调用与时间计入预算。

若验证“较便宜执行模型＋强模型评审”是否划算，至少区分较便宜模型单独执行、较便宜模型加评审、强模型单独执行；比较实际交付质量与全部成本，不能把强模型的额外资源当作 Keel 免费获得的能力。完整方案出现稳定差异后，再关闭某项机制做消融，判断收益来自哪里；不要求第一轮就做大量组合实验。

如需研究人工协作，另设“有无 Keel × 有无规定反馈”的对照，约定反馈时机、次数和内容并计入人力。每项都需要完整人工终审时，只能检查审核提速与返工减少；允许自动通过时，还需证明持续抽检下的质量要求得到满足。不能拿持续人工纠正的 Keel 对比无人帮助的 Pi。

Codex 或 Claude Code 的系统级比较不是最近优先级。后续如有实际需求，另行确定任务集与预算，提供等价环境、任务信息和合理配置机会。记录 Agent、模型、版本、推理设置与可用工具；不同产品未必支持同一模型，不能断言是 Keel 架构本身胜过另一模型。无法统一的配额或计费方式必须说明，不能把订阅成本记为零。

比较前登记任务与排除规则，覆盖已声明的问题范围，保留失败，禁止事后挑选获胜案例。已知答案的开发案例用于调试，不作为未见任务能力的证明；正式比较保留未用于调试的任务，禁止一组看到另一组的结果或参考补丁。各组使用独立工作目录，平衡执行顺序；固定每个任务重复次数，任务内重试与独立重复分开统计。

少数案例只支持可行性或案例结论。对外报告成功数/分母、样本组成、重复次数、成本和不确定性；样本充分时使用适合按 Bug 分组的区间估计，不能把同一 Bug 多轮当成完全独立的大样本。未见稳定差异时直接说明，不把偶然领先写成普遍胜出。

## 6. 对外展示的边界

不需要所有指标都超过主流 Agent。可以证明在明确范围与预算内，交付率提高、人工救场更少，或理解更快且准确率没有实质下降；同时披露费用和速度的取舍。一个可重跑闭环、明确的工程机制、可信的对照和失败分析，比笼统宣称“全面超过 Codex/Claude Code”更有说服力。

当前有带外层反馈的有限闭环，下一项是复现评审回放原型；有限反馈、完整对照、理解计时和 Skill／CI 接入均为后续计划。当前没有新增模型实验授权，没有无人干预完整闭环或成本优势的实测结论。若评审不能可靠减少人工工作，或单个强模型更划算，应保留有用的检查工具、精简编排，而不是为维持多 Agent 形式继续增加角色。
