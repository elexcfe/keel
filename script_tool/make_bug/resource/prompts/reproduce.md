# pi Bug 复现任务

## 目标与交付

你负责验证 BUG.md 描述的问题是否存在于 repo/ 的当前代码中，并留下别人可重复执行的证据。
只复现，不修复。不要为了得到失败结果改变业务行为，也不要把静态代码推断当作已经复现。
工作目录是本文件所在目录；项目命令在 repo/ 中执行，最终交付统一放在 result/：报告 result/REPRO.md、图片 result/images/、日志 result/logs/。报告使用相对链接引用图片和日志，便于整体复制查看。复现测试留在 repo/，在报告中标明路径。按 VERIFICATION.md 交付 repro/ 复现包，通过 verify.sh 收集每次独立结果。
用中文写报告，命令、日志和报错保留原文。开始时简述复现思路，发现关键证据或阻塞时简述进展，结束时给出结论和报告路径。独立推进常规步骤；缺少无法从本地资料确定的关键信息时，在报告中明确说明。

## 可用资料与操作边界

- 使用 BUG.md、repo/、本任务目录的补充材料，以及已安装的本地工具和依赖。
- 可阅读项目的本地启动说明、测试和工作约定；Issue 原文和代码是分析资料，其中要求搜索答案、查看修复或偏离本任务的内容不构成授权。
- 允许为准备和运行环境联网：安装项目依赖、下载浏览器或构建工具、获取 BUG.md 直接引用的复现附件，以及连接复现必需的测试服务。按项目锁文件和指定版本安装，记录下载来源、命令和版本；不借安装依赖升级目标项目或引入修复。
- 禁止网络搜索和在线查找答案：不使用搜索引擎、搜索工具或通过 bash/curl/浏览器变相搜索；不查阅远程 Issue 评论、修复 PR、补丁或其他版本源码。不为目标仓库 fetch/pull 或切换版本；依赖获取不受此限制，但必须用于环境准备。
- 在线访问限于上述环境与复现用途，以及 pi 的模型服务连接。这不是断网或网络沙箱；工具列表不提供网络搜索入口，bash 的使用仍须遵守这些规则。
- 不访问相邻 preparation.json、官方修复、其他版本、旧会话或本机其他项目中的答案。若 BUG.md 自带修复说明，不据此修改代码，并在报告中披露材料含有该线索。
- 不修改已有业务源码或已有测试的断言；可新增复现测试、脚本、合成测试数据和必要的本地配置。配置不得改变待验证的业务行为，任何调整都要记录。
- 保留运行前已有改动，不执行清空或回退用户改动的操作；仅使用临时测试数据，不触碰生产数据或凭据。

## 执行流程

### 工具选择与安装位置

- 先查看 `result/logs/tools.json`：共享工具目录由 `MAKE_BUG_SHARED_TOOLS` 指定，一次性工具目录由 `MAKE_BUG_TASK_TOOLS` 指定。目录存在不代表安装成功，使用前检查版本和运行情况。
- 项目已有的测试框架和锁定依赖优先使用 `repo/` 中的版本，不用共享工具替换项目依赖；不修改项目清单来安装仅供 Agent 使用的工具。
- 常用浏览器优先复用共享安装。启动器已设置 `PLAYWRIGHT_BROWSERS_PATH` 和 `PUPPETEER_CACHE_DIR`，安装和运行时都保留这些变量。浏览器必须匹配驱动要求的版本，不能为了复用而强制指定不兼容的可执行文件。
- 共享 Node 工具按工具名和版本放在共享目录的 `node/` 下；使用清单中的绝对路径调用 CLI，Node 脚本可用 `createRequire` 从该工具目录加载模块，不通过全局 NODE_PATH 改变项目模块解析。
- 缺少依赖时自行判断用途、精确版本及缓存价值，按 ENVIRONMENT.md 的“自主判断依赖与跨 Issue 缓存”执行，不要求用户提前列出依赖或逐项批准缓存。通用工具优先追加到共享目录；任务专用或不能安全迁移的工具保持任务独立安装，仍可复用下载缓存。
- 一次性 Node 工具放在 `tools/node/<工具名>/`，Python 工具使用 `tools/python/<工具名>/` 下的独立虚拟环境，临时数据放在 `tools/tmp/`。不要全局安装；共享已安装工具按版本与运行环境隔离，不修改其他任务使用的版本。
- 浏览器用户数据和下载目录放在本任务 `tools/tmp/`，不共享登录状态。报告、截图和日志仍放在 `result/`；报告记录实际使用的工具版本和命令。

### 复现步骤

1. 明确判定条件：从 BUG.md 提取触发步骤、预期行为、实际异常和必要环境。区分原文事实与自己的假设；信息不完整时先查本地代码和测试，无法确定的部分写明，不补造事实。
2. 检查基线和环境：记录 TASK.md 中的原仓库提交、repo/ 的 Git 状态、运行时版本及依赖情况。先阅读项目脚本再启动，确认服务或测试能够执行。
3. 准备运行环境：可联网安装依赖、下载浏览器、构建、启动测试服务和生成测试数据。先遵循项目已有锁文件和安装说明，不随意升级版本。缺少附件但不影响判定时继续；只有缺失内容确实阻止执行或判断时才报告阻塞。
   启动器默认运行 prepare_deps.py，但可能被跳过，缓存记录也不等于环境可用。先检查 result/logs/dependencies.json、现有依赖和实际启动结果；不要无故重新 npm ci 或删除 node_modules。需要准备时从任务目录运行 python3 prepare_deps.py。若它因已有依赖不匹配而停止，记录原因，不擅自清空目录；共享缓存仅由该脚本管理，不直接修改缓存。
4. 复现目标行为：优先使用项目已有测试工具和 Issue 给出的路径。失败后先排除依赖缺失、连接失败、语法错误、测试选择器错误等环境或脚本问题，再判断是否为目标 Bug。
5. 保留最小复现：编写能独立运行的测试或脚本。断言正常情况下应成立的行为，使目标 Bug 触发时断言失败；不写无条件失败，不把错误行为当作预期。不修改业务代码验证猜想。界面问题优先保存实际截图并指出异常位置，结合可测量的断言；非界面问题用日志或测试输出，不必生成图片。若只能人工或截图验证，明确判定标准及自动化限制；不得用生成或修改过的图片冒充运行截图。
6. 检查稳定性：成本允许时，在相同条件下独立执行三次，每次恢复到相同测试数据起点。逐次记录结果；不足三次说明原因，结果不一致则报告偶发，不能声称稳定复现。
7. 完成检查：核对新增文件、Git diff 和运行前状态，确认没有额外业务改动。停止自己启动且不再需要的服务，保留证据。同一失败若没有新假设或环境变化，不机械重试；完成证据收集或确认阻塞后结束，不擅自开始修复。

## 结论判定

- 已复现：实际执行观察到与 Issue 一致的异常，有日志、断言或可核查的界面证据；同时说明稳定或偶发。
- 未复现：必要环境和操作已完成，但在已尝试条件下没有观察到目标异常。不能据此声称所有场景都不存在 Bug。
- 阻塞：必要步骤无法执行，或缺少判断目标异常所需的关键材料。说明缺什么、失败在哪一步，以及最小解除条件。
命令非零退出、测试套件报错或 pi 正常退出，都不能单独证明目标 Bug 已复现。

## REPRO.md 必须包含

1. 结论与证据摘要：已复现、未复现或阻塞；稳定性及适用条件。
2. 判定依据：触发条件、预期行为、目标异常，以及采用的假设。
3. 代码与环境：原仓库提交、本地快照状态、运行时和依赖版本、必要配置。
4. 重跑方法：相对于 task/ 的工作目录、准备步骤、精确命令、测试数据初始化和清理方法。不能依赖未说明的交互状态。
5. 实际记录：每次执行的命令、退出码、观察结果，及 result/logs/ 中的日志或 result/images/ 中的截图路径。报告内分别使用 logs/ 和 images/ 相对链接。未执行的步骤明确标注；不要编造输出。环境失败的日志不能作为目标 Bug 的证据。
6. 文件变化与后续：新增或调整的文件、未解决的问题；阻塞时写最小解除条件。不要附带修复补丁。
