# Keel 项目计划

Keel 围绕现有编码 Agent，组织 Web Bug 的复现、修复、验证和交付，目标是减少工程师反复解释、等待、审核和返工的时间。运行与证据底座继续复用；下一阶段优先研究外层评审能否被可靠地辅助或自动化，并测量正确交付所需的人力与总成本。

本文规定开发顺序、技术边界和进入下一阶段的条件；产品目标见 [产品说明](keel-product-brief.md)，接入方式见 [Pi 接入方案](keel-pi-integration-plan.md)，指标与公平对照见 [评测方案](keel-evaluation.md)。Issue 保存整体状态，具体计划保存实施步骤，不在这里维护第二套进度。

## 1. 当前基础与下一项任务

已有依赖清单、场景执行、同会话修复、运行监测、报告检查以及任务和交付入口继续使用。Actual 的两条已声明路径已在外层反馈后完成修复验收；这证明了一次有限范围的可行性，不证明首次交付、无人干预闭环或相对 Pi 的增益。统一入口的主要验证仍是离线测试，不能用入口可运行代替真实效果。

**下一项任务是 [#14“复现评审回放原型”](https://github.com/elexcfe/keel/issues/14)**，具体范围、数据边界和验收条件见 [实施计划](../plans/reproduction-review-replay.md)。用户已授权先盘点材料、实现最小只读入口并运行离线测试；真实模型调用暂不启动，待明确模型与费用预算。离线实现和缺口见实施计划。

| 顺序 | 可独立验收的结果 | 进入下一步的条件 |
| --- | --- | --- |
| 下一项：复现评审回放 | 基于冻结产物给出有证据引用的评审建议，形成漏判、误判、无法判断和费用报告 | 评审建议可追溯；开发样例与留出样例分开；明确适用范围与剩余缺口，不以少量样例预设可靠性 |
| 回放后再决策：有限自动反馈 | 在现有任务入口接入退回执行者、重新验证和再次评审，受统一轮数与预算约束 | 先登记允许的任务范围、错误放行容忍度与评测方案；达到依据充分的准入条件后才开放对应能力 |
| 流程可评估后：原始 Issue 完整对照 | 从相同 Issue 出发比较真实交付、人工工作量、错误放行及完整成本 | 输入、隐藏终局标准、预算和反馈政策提前固定；运行中的人工或额外 AI 参与均可追踪 |
| 收益与需求明确后：轻量接入 | 按用户工作方式提供 Skill 入口与 CI 检查，复用同一套 CLI | 核心工具稳定且存在明确接入需求；不预先要求用户更换编码 Agent |

现有任务的处理方式：

- [#11](https://github.com/elexcfe/keel/issues/11) 与 [#12](https://github.com/elexcfe/keel/issues/12) 的最小任务/交付入口作为底座，真实效果验证仍按各自计划与评测方案执行，不重新建设。
- [#9](https://github.com/elexcfe/keel/issues/9) 的真实 FFmpeg 集成检查保留为已有验证缺口；是否影响某个评审案例，以该案例实际需要的证据读取方式判断，不为回放原型扩大视频工具范围。
- [#10](https://github.com/elexcfe/keel/issues/10) 的动态预算提示后置，只有记录显示它是当前瓶颈时再安排。
- [#13](https://github.com/elexcfe/keel/issues/13) 的视频导航按需后置；画面编号实验路线已终止，结论见 [实验记录](../plans/video-marker-experiment.md)。
- [#8](https://github.com/elexcfe/keel/issues/8) 继续关联产品与评测口径的调整。未形成单独验收目标的后续想法不批量创建 Issue。

## 2. 范围与职责

先处理 TypeScript / React 项目中环境可重建、现象可观察的 Web 行为问题。Issue 原文与附件、故障版本源码和相同基础环境可以作为输入；人工补充根因、复现脚本、断言或修复答案须另行记录，不能算成 Agent 自主产出。

| 职责 | 当前承担者与后续边界 |
| --- | --- |
| 环境准备、复现、修复和报告 | Pi 是当前执行主体；场景、数据、断言、业务修改和报告仍由它生成 |
| 运行、记录和机械检查 | Keel 现有程序负责预算、执行状态、场景/源码版本和证据引用一致性 |
| 复现及交付的语义判断 | 当前依赖外层审核；先验证评审 Agent 的建议质量，再决定是否接入自动反馈 |
| 最终效果评价 | 与执行工作流隔离的验收依据和评测方；不能让工作流中的评审 Agent 给整个系统自评成功 |

未来首先只考虑执行者和评审者两个角色。较便宜模型承担常规执行、强模型集中在复现准入和最终交付关口，是待验证的成本方案；若单个强模型更划算，就采用更简单的方案。没有效果依据前不建设动态组队、投票或通用多 Agent 平台。

## 3. 复现评审回放的技术安排

第一项回放只评复现准入，不自动修复、不自动退回 Pi，也不授予正式验收权。输入是冻结的原始 Issue、场景/断言、问题版本记录和必要证据；输出是独立保存的“建议通过／退回／无法判断”及对应材料引用。

先复用 `evidence.py`、`repair.py` 和 `delivery.py` 中适用的机械检查，标明缺文件、摘要不一致、检查未执行等事实；再让评审 Agent 判断观察是否对应原问题、断言是否充分、说明是否有依据。复现不需要假装已有修复前后两轮；只读回放也不承诺重新执行项目。

评审先依据原始 Issue 列关注点，再读取执行者的解释。标注答案、旧的外层验收结论、修复后的代码或记录不得进入评审输入；这些内容可供独立标注者使用，但须与评审可访问材料隔离。机械校验成功不能自动变成语义通过。

已有任务产物和原始证据不得改写。独立标注、评审输出和合成错误样例另存并标明来源；同一 Issue 的不同轮次按同一组划分，不能分别放入开发集与留出集。细节由 [回放计划](../plans/reproduction-review-replay.md) 统一维护。

## 4. 有限反馈的后续接入

回放有依据后，再评估在 `task_flow.py` 的准入与交付审核位置接入评审调用；运行、快照、预算和正式检查沿用现有模块。此阶段需要独立任务和验收，回放原型不隐含授权。

- 正式决定、模型建议与机械检查分开记录；建议通过不会自动写成 `accepted`。是否委托模型作某类准入决定，必须按事先验证的范围明确配置和记录来源。
- 反馈要求引用具体问题和证据，由 Pi 自行纠正；评审者不得补写 Pi 产物或改写历史证据。
- 阶段切换和重试共用总时间/费用，记录轮数、用量未知和中断；达到边界就保存未完成状态，不自动增加预算。
- 无法判断、反复退回和需要额外权限的任务明确交接。人工处理与抽检的时间和结果进入成本记录。
- 自动通过的结果也要抽检，不能只看有分歧的任务；两个 Agent 都同意仍可能共同误解需求。

当前要求外层准入后才能修复的规则保持不变。“未审核候选直接修复”不是主线，也不能为实验伪造准入；若以后要研究该变体，应单独标明系统变化、风险与对照范围。

## 5. 评价什么，怎样决定继续投入

三个结论分开验证：评审建议是否有效、加入反馈后任务是否更容易完成、完整流程是否节省人力与总成本。前一项成立不自动推出后一项。

- 回放：统计错误放行、错误驳回、无法判断与可判定覆盖；保留每个问题的结果和费用。已有 Actual 材料用于开发和错误分析，不作为未见任务能力证明。
- 完整流程：从原始 Issue 开始，两组自行生成复现和检查；隐藏验收只在结束后使用，不回传作为导航。预先给已审核基线的试验只能证明修复阶段效果。
- 人工收益：分别比较必须全审的任务中审核时间是否减少，以及允许例外处理/抽检的任务中总工作量是否下降；最终质量需由独立评测确认。
- 成本：包括执行模型、评审模型、工具、失败重试、返工、持续人工审核/抽检以及维护摊销。开发校准与实验统一判卷成本单列披露，不把上线仍需要的人力挪出账本。

比较至少考虑较便宜模型单独执行、较便宜模型加较强评审、强模型单独执行；若要归因于 Keel 的某项机制，再在同样模型与预算下做对应消融。样本量、质量容忍范围和预算在运行前登记，小样本零漏判不能证明可靠。

没有观察到稳定增益就缩减机制或收窄适用范围。早期的成功率、二十秒理解等数字没有测量依据，不再作为当前目标、排期或验收门槛；后续阈值需按实际任务与成本制定。

## 6. 交付形态和后置方向

近期保留 Pi 和现有 CLI，不增加独立客户端、RPC 服务或深度 SDK 嵌入。核心检查应可脱离编码会话运行。未来 Skill 负责引导 Agent 使用工具，CLI 执行和记录，CI 复用必要检查；这是接入方向，尚未实现 Codex/Claude Code Skill 或 CI 集成。

基础交付继续包含环境重跑材料、行为证据、代码差异、修改原因和未验证范围。复杂 UI 流程按需要录屏，静态或非界面问题可用截图、日志或请求记录；不要求自动剪辑、逐帧分析或独立播放器。

代码关系图、AST/调用关系与影响分析、更多语言与后端、完整自动恢复、外部团队试点均按具体瓶颈再决定。现有报告先做到触发方式、原因、改动和证据可核查，不把复杂图形当作交付前置。旧的人员配置和固定工期估算不再沿用，排期以阶段结果及实际投入为依据。

## 7. 主要风险和处理方式

| 风险 | 处理方式 |
| --- | --- |
| 模型共同接受错误结论 | 独立原问题视角、原始证据核查、通过样本抽检和隔离的终局判定；不把模型共识当真值 |
| 评审读取旧结论或修复答案 | 冻结允许访问的材料，独立保存标签和终局资料，记录实际输入与来源 |
| 评审过严造成无效返工 | 同时统计错误放行、错误驳回、无法判断和总成本，不只追求更低通过率 |
| 标注有争议或证据不完整 | 保留争议与无法判定，不制造确定标签；登记纳入与排除规则 |
| 任务与报告版本不一致 | 继续使用现有摘要、轮次和引用校验；机械一致不替代语义验收 |
| 调用、反馈或多角色增加成本 | 限制角色、轮数和预算，并与单强模型比较；效果不清楚就保持简单 |
| 测试环境或材料使用越界 | 保持隔离环境与已有权限边界；记录模型服务和允许发送的材料，不写生产数据 |
| 核心接口与资料分叉 | 复用现有模块，变更时同步相关说明和索引，已实现与计划明确区分 |

相关资料的路径和用途统一见文档索引。当前只完成方向、计划和任务登记，不启动代码开发、模型调用或新实验。
