# Keel 评测方案（第一版）

利用日常修 bug 的任务记录，验证 Keel 能否自动完成检查、在交付前发现并修正问题。不额外运行付费评测，不做人工计时或竞品对照。

## 指标一：验证流程完成率

**验证流程完成率 = 完成以下流程的任务数 ÷ 全部已结束的修复任务数。**

1. 修复前成功复现 bug。
2. 修复后，同一复现检查通过。
3. 相关回归测试运行完毕，记录通过或失败结果。

没有可运行测试、环境失败、中途放弃，均计入分母，标记为“验证未完成”。回归测试运行完毕但存在失败，仍属于流程完成，不代表修复成功。

## 指标二：交付前自动纠错成功的任务数

同一任务满足以下条件，计为 1 个：

1. AI 首次修改后，系统自动验证发现问题仍存在或出现回归。
2. 无需用户打回，系统自动继续修改。
3. 最终复现检查通过，相关回归测试没有新增失败，再交付用户。

例如：首次修改 → 测试失败 → 自动再次修改 → 验证通过 → 交付，计为 1 个任务。中间重试多次也只计 1 个。

同时保留“发现问题但未自动修好”的任务数。环境故障不算发现修复问题。

## 最小记录

每个任务自动保存：任务编号、验证流程是否完成、自动纠错结果（未触发／成功／未修好），关联已有测试日志即可。用户最终只需选择“接受”或“仍需修改”，不作为上述自动指标的判定依据。

汇总展示：

> 共结束 N 个修复任务，X 个完成验证流程（X/N）；Y 个在交付前自动纠错成功，Z 个发现问题但未自动修好。

这些指标用于证明自动验证和纠错能力，不等同于真实修复正确率、节省的人工时间或减少的用户返工次数，也不证明优于其他工具。
