# Keel：DeepSeek Harness 插件方案

> 日期：2026-09-13
> 状态：已确定采用插件形式；本文记录模块分工和开发顺序，具体接入方式在开发时验证。
> 本文说明插件分工和接入要求；产品说明概括目标与边界，项目计划概括开发顺序和完成标准。关于产品运行形式和模块划分，以本文为准。

## 1. 我们决定怎么做

Keel 采用 DeepSeek Harness 插件的形式开发。几个插件分别负责不同工作，组合起来完成一次 bug 修复。

DeepSeek Harness 提供现成的 Agent 编码能力：读取项目、分析问题、修改代码。Keel 负责把问题复现出来、检查修复是否有效，并向人解释改动。

核心能力独立开发，插件负责把这些能力接入 Harness。比如，运行测试和生成验证报告的代码，不需要打开 Harness 也能单独运行和测试。这样以后修改某个模块，或者接入其他工具，不必重写核心代码。

选择插件形式主要有两个原因：

- 各模块可以分开开发、测试和更新。
- 直接使用 Harness 已有的编码能力和交互界面，减少基础功能的重复开发。

## 2. 要做哪几个插件

先按四个插件划分。这里是职责划分，不代表第一天就要全部做完。

| 插件 | 负责的事情 | 交付的结果 |
| --- | --- | --- |
| 流程与审核 | 管理一次修复的进度，安排各阶段工作，在关键步骤等人确认 | 任务进度、确认记录、最终结果页面 |
| 复现与验证 | 把 bug 变成能重复运行的检查步骤，修复后再检查一次，并运行已有测试 | 复现用例、测试结果、截图和日志 |
| 定位与修复上下文 | 整理 bug、文档、日志和相关代码，帮助 Agent 找到问题并开始修复 | 可能原因、相关代码位置、交给 Agent 的修复说明 |
| 改动理解 | 分析修改了什么、可能影响哪里、有没有超出原先约定 | 改动说明、影响关系图、需要人重点检查的地方 |

### 2.1 流程与审核插件

它负责回答：“这个 bug 现在处理到哪一步了，接下来该做什么？”

具体工作：

- 创建任务，保存用户提供的 bug 描述、项目位置和环境信息。
- 按顺序安排复现、定位、修复、验证和报告生成。
- 保存进度，中断后能知道哪些工作已完成、哪些需要重新执行。
- 在三个地方请人确认：复现的是不是这个问题、定位方向是否同意、最后是否批准合入。
- 汇总测试结果和改动说明，展示给用户。

任务走到哪个阶段，由这个插件统一管理。其他插件完成工作后交回结果，不各自决定整条流程怎么走。

### 2.2 复现与验证插件

它负责回答：“问题能不能稳定出现？修改后，同一个问题还会不会出现？”

具体工作：

- 根据 bug 描述，借助 Agent 编写浏览器检查脚本，第一版使用 Playwright。
- 准备测试所需的数据，每次运行前恢复到相同起点。
- 在修复前连续运行至少三次，确认每次都因目标 bug 而失败。
- 保存检查脚本、预期结果和失败记录，让人确认复现正确。
- 修复后原样重跑已确认的检查，并运行项目已有的相关测试。
- 收集截图、日志和测试结果，生成验证报告。

复现和验证先放在同一个插件里，因为它们用的是同一套检查步骤、测试数据和运行环境。内部代码可以分别维护，但检查标准必须一致。

例如，问题是“保存后备注没有追加文字”，检查就应当读取保存后的备注内容。页面截图看起来正常，不能代替这个检查。

结果要明确区分：

- **通过**：目标问题的检查通过，并列出其他测试的实际结果和覆盖范围。
- **失败**：目标问题仍存在，或者发现其他测试未通过。
- **无法验证**：环境启动失败、缺少数据等原因导致检查无法完成。

启动失败不能算复现成功；没有运行的测试也不能写成通过。测试通过只说明已检查的范围内没有发现问题，不代表整个项目绝对没有其他问题。

### 2.3 定位与修复上下文插件

“修复上下文”就是 Agent 修代码前需要知道的背景和材料。

具体工作：

- 整理预期行为、实际行为和复现步骤。
- 收集相关报错、请求记录和项目文档。
- 找到可能相关的文件和函数，说明判断依据；不确定的原因要标明。
- 将这些材料交给 Harness Agent，让它分析并修改代码。
- 记录 Agent 准备改什么、为什么改，以及实际交回的修改。

Keel 不另做一套编码 Agent。第一版可以先由人指出相关代码位置，后续再逐步提高自动定位能力。

### 2.4 改动理解插件

它负责回答：“这次到底改了什么，我该重点看哪里？”

具体工作：

- 比较修改前后的代码，归纳真正影响行为的变化。
- 找出改动可能影响的其他文件、函数或页面。
- 对照已确认的修复范围，提示可能超出约定的改动。
- 用简短说明和关系图展示结果。

例如：“修复了备注追加规则，同时修改了所有规则的执行顺序，需要重点检查其他规则是否受影响。”

第一版先做到文件和函数层面的说明，再逐步增加调用关系和影响分析。无法判断的影响要标明，不能把猜测写成事实；修改了另一个文件也不自动等于越界，需要结合修复目的判断。

## 3. 插件下面还需要哪些公共模块

这些模块供插件共用，先作为普通代码包或独立运行的程序实现，不要求分别做成插件或远程服务。

| 公共模块 | 通俗解释 | 谁会用到 |
| --- | --- | --- |
| 隔离运行环境 | 在专门的测试环境里启动项目、准备数据、运行浏览器和测试，避免影响生产 | 复现与验证、修复过程 |
| 任务与结果保存 | 保存每次任务的检查脚本、代码版本、日志、截图和确认记录 | 四个插件 |
| 代码关系分析 | 找出文件之间、函数之间的引用和调用关系 | 定位与修复上下文、改动理解 |

第一版优先接入本地测试环境或已有测试站点，代码关系分析可以后做。插件本身不会自动提供环境隔离，执行程序仍要明确在哪里运行、允许访问什么。

## 4. 一次修复如何完成

以“保存交易后，备注没有追加规则要求的文字”为例：

1. 用户提交问题，流程插件创建任务。
2. 复现插件写出检查步骤，连续三次观察到追加文字缺失。
3. 用户确认：“对，这就是我要修的问题。”
4. 定位插件整理相关日志和代码，给出可能原因，用户确认定位方向。
5. Harness Agent 根据这些材料修改代码。
6. 验证插件用原来的检查步骤重跑，并执行其他相关测试。
7. 改动理解插件说明改了哪里、可能影响什么。
8. 流程插件展示证据和改动说明，由用户决定是否批准合入。

任何阶段遇到失败或信息不足，都应显示原因。需要重新修改时，保留上一轮结果，再开始下一轮，不能覆盖掉失败记录。

## 5. 为了能分开迭代，提前约定什么

### 每份结果都能找到来源

检查用例、代码修改和报告都要标明属于哪个任务、哪次运行，以及当时使用的代码版本。有未提交修改时，也要记录这份修改，不能只保存提交号。

### 插件之间交接固定格式的材料

例如，复现插件交出“检查步骤、预期结果、实际结果和文件位置”，验证插件交出“通过、失败或无法验证，以及对应证据”。这些信息用固定字段保存，不能只靠从聊天文字里猜。

字段有变化时，要明确格式版本，让使用它的其他插件知道是否需要更新。

### 已确认的检查标准不能偷偷改变

复现确认后，保存固定版本的检查脚本和预期结果，验证程序用这一版检查修复。修复 Agent 不能通过删除检查或放宽条件来获得通过结果。

如果检查本身确实有问题，需要重新确认，并在修复前的代码上重新建立失败记录。测试结果由实际执行检查的程序生成。

### 一处修改，不要求所有模块一起重写

插件只负责接入 Harness 和展示入口。复现、验证、代码分析等核心代码各自可以单独测试。接入 Harness 的部分集中维护，并固定使用经过验证的 Harness 版本。

## 6. 先做什么，后做什么

### 第一阶段：跑通一个真实 bug

- 做流程插件的最小版本，能创建任务、显示进度、保存人工确认。
- 做复现与验证插件，能保存失败记录、修复后重跑并输出报告。
- 先由人整理修复材料，直接交给 Harness Agent 修改代码。
- 使用已经克隆的 Actual Budget 项目，从靶场清单里的一个 bug 开始。

这一阶段完成的标准：同一个用例在修改前稳定失败、修改后通过；报告列出已有测试的结果；人能够查看代码修改和证据。还要检查：改掉断言、测试没运行或环境启动失败时，系统不会给出验证通过的结论。

### 第二阶段：减少人工准备工作

- 加入定位与修复上下文插件，自动整理日志和相关代码。
- 增加失败重试和中断恢复，避免每次都从头开始。
- 用靶场里的其他 bug 检查哪些步骤可以复用、哪些仍需人补充信息。

### 第三阶段：让改动更容易审核

- 加入改动理解插件。
- 先做清楚的改动说明，再加入代码关系图和影响分析。
- 对照修复前约定的范围，提示需要额外审核的改动。

开发期间，浏览器和相关测试可以由独立进程执行。暂时不需要为了插件化，先建设一整套远程服务。

## 7. 与原计划的对应关系

| 原计划模块 | 采用插件形式后的安排 |
| --- | --- |
| Keel 控制面 | 流程与审核插件，结合 Harness 界面实现 |
| 复现引擎、验证引擎 | 复现与验证插件，内部保留各自的核心代码 |
| 定位引擎 | 定位与修复上下文插件 |
| 修复适配层 | 缩小为向 Harness Agent 交付材料、记录计划和接收修改 |
| 理解与影响分析层 | 改动理解插件 |
| 活代码图服务 | 公共的代码关系分析模块，初期不要求独立部署 |
| 隔离执行环境 | 公共的隔离运行模块 |
