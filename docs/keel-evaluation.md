# Keel 评测方案

评测围绕两个产品目标：**提高端到端修复交付率；帮助人更快、准确地理解 Bug 与修改。** 当前先完成真实修复闭环，利用已授权的日常任务积累记录，不因本方案自动启动模型调用、人工受试测量或新的付费实验。后续对照的任务集、次数和总预算须另行确定并获授权。

本方案定义要证明什么，不代表已有成绩。已完成的复现、报告交付或进程清理验证不能算完整修复成功；历史记录不够支持新口径时标为“无法按新口径判定”，不回填成功。已有 [Pi 会话拆分实验](pi-session-experiment.md) 比较的是 single/split，不是基础 Pi 与 Pi＋Keel 的增益，也不是与主流 Agent 的比较。

## 1. 端到端交付率

**端到端交付率 = 在预定预算内、无人工救场且通过独立交付验收的任务次数 ÷ 预先登记且已结束的有效任务次数。**

一次任务从约定的 Bug 描述、源码和环境起点开始，到交付代码、验证证据和说明并等待审核结束；不要求自动合并或部署。启动前确定时间/费用预算、最大重试次数、所需回归范围和人工参与边界。任务内部的失败与重试不另算多个任务；比较中同一 Bug 的预定独立重复按任务次数计，同时报告不同 Bug 数量，不能靠反复跑一个容易案例增加样本。

### 什么算成功交付

所有条件同时满足，才计入分子：

1. 修复前以真实操作或检查观察到目标 Bug，独立验收确认它对应原问题；环境错误、导航超时不能冒充 Bug。
2. Pi 产出修复；修复后同一已确认的场景、断言和数据条件通过。若检查本身需要纠正，重新评审并在修复前版本上建立有效失败记录，保留版本差异，不能放宽断言制造通过。
3. 预先约定的相关回归检查已运行，无本次引入的失败。已有失败单列并有依据；无法分清新旧失败、必需检查未运行时不能计成功。
4. 在预算内交齐可重跑的代码、场景、运行记录及说明；证据、结构化检查和报告一致，说明原因、改动、验证范围与限制。文件齐全、Agent 退出 0 或测试通过，均不能单独判成功。
5. 独立验收者按统一标准核对代码、证据并原样重跑必要检查，确认修复针对目标问题；不能只采信生产产物的 Agent 自评。验收记录另存，不修改原报告或原始证据。

对闪烁、瞬间消失等问题，原始视频清楚证明操作与异常即可作为主要界面证据，不强求截图截中瞬间。Pi 必须说明以视频为主，提供具体轮次的视频链接、异常时间段和应观察的现象；截图说明仍须准确。

### 失败、人工介入与预算

| 情况 | 统计方式 |
| --- | --- |
| 环境准备失败、无可运行检查、超时、超费用、中途放弃、交付部分完成或验收不通过 | 有效任务计入分母，不计分子，保留原因 |
| 预算内自主重试、恢复环境、发现错误后修正 | 可计成功，同时计入该任务总耗时、费用和重试数 |
| 人给出关键定位/补丁、修复脚本或数据、补写报告、救活环境 | 记录人工救场；即使最终通过，也只列为“辅助完成”，不计自主交付分子 |
| 预先约定的复现/定位确认、权限批准、最终审核 | 不自动算救场；保留次数、内容和等待时间。若确认时给出额外解法，则按救场记录 |
| 已知的启动前材料准备 | 明确列为输入条件，不能声称由 Agent 自主完成；各组条件一致 |
| 外部执行器故障导致试验本身无效 | 依预先约定规则、独立证据单列；保留该次记录和成本，不能因某组失败而事后排除 |

生产阶段预算计入环境准备、模型调用、工具运行、重试及收尾；外层验收另记耗时与成本，不能拿验收时间继续补产物。人工等待是否暂停执行预算在开始前统一约定，实际端到端墙钟时间仍报告。费用为估算时注明来源与缺项。

汇总必须同时给出成功数/总次数、不同 Bug 数、失败原因、人工救场次数、费用和耗时。报告全部任务成本以及每个成功交付分摊的总成本（包含失败花费）；零成功时后者不可计算。不要用更大预算下的胜出声称效率更高。

## 2. 帮助人理解 Bug 与修改

目标是让审核者更快作出正确判断，不以报告长度、图片数量、关系图复杂度或主观“看起来清楚”作为主要成绩。

在同一任务上，要求不熟悉该任务的审核者回答固定问题：

- 怎样触发 Bug，用户会看到什么异常？
- 原因是什么，哪些是已证实事实，哪些仍是假设？
- 改了哪里、为什么能解决问题，影响范围是什么？
- 哪些检查真正运行并通过，哪些部分未验证，是否还需补充证据？

依据源码、差异和实际执行证据，由独立评审预先制定答案与评分规则。主要记录**完成问题所需时间与回答正确率**；同时保留超时/未答、关键风险误判和查找证据所需的追问。不能仅筛选答对的人计算时间，或因读得更快而忽略正确率下降。满意度只作补充。

先用已有任务材料做小规模可用性观察，发现说明缺口；正式对照再采用以下安排：

- 同一份已冻结的修复与证据，比较基础说明和 Keel 说明，尽量固定信息来源，使差异来自组织与解释方式。若比较的是不同 Agent 的完整交付，注明内容质量也不同，不能把差异全归因于报告形式。
- 隐去工具名称，随机/交叉安排不同任务的材料；避免同一人先看一份答案再看同一 Bug 的另一份。记录参与者经验，平衡任务难度与阅读顺序。
- 预先确定人数、题目、时间上限和可接受的准确率差异；报告人数、分数、时间分布及失败，不预设“20 秒理解”之类未经验证的成绩。

没有实际人员参与测量时，仅能说“交付了有依据的说明”或“通过内容检查”，不能宣称节省了审核时间。自动检查和 AI 评审可帮助检查一致性，不能代替真实人的理解效果。

## 3. 辅助指标与最小记录

保留旧指标，帮助解释交付在哪里失败：

- **验证流程完成率：** 修复前复现、修复后检查、相关回归均实际执行的任务次数占全部已结束有效任务次数的比例。测试运行后失败仍可能满足“流程完成”，不能替代端到端交付率。
- **交付前自动纠错：** 系统发现首次修改仍有问题或引入回归，在无人工救场情况下自行修正，最终目标检查通过且相关回归无新增失败。分别统计已纠正和未纠正；环境恢复另记，不冒充修复纠错。

复用现有任务、会话和场景记录，不为此先建设评测平台。每次至少能追溯：任务/轮次、源码与输入版本、工具/模型配置、预算与实际成本时间、重试、人工介入、原始证据、独立验收与失败原因。理解测量开始后才增加匿名参与者、材料版本、题目评分和用时记录；当前未采集的字段标缺失，不推算为零。

## 4. 分阶段验证

| 阶段 | 目的和工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| A：先完成修复闭环 | 先用一个真实 Web Bug 打通 Pi 自主复现、修复、同场景验证、相关回归和解释交付；再用少量不同问题检查可复用性，保留全部失败 | 至少一个完整案例经独立验收；输入、交付规则和失败记录可复用，费用/耗时可追踪。单个案例只是可行性证据 |
| B：同模型对照 | 比较基础 Pi 与 Pi＋Keel，回答增益是否来自 Keel；先小规模试验协议，再按预算扩展。用冻结材料开始理解效果测量 | 评测协议、验收标准、样本和预算明确，结果可重复且可解释；若效果不清楚，先排查，不急于做竞品宣传 |
| C：主流 Agent 对比 | 流程稳定后，先选择 Codex 或 Claude Code 中一个，再按成本决定是否增加另一个；比较整个工具流程的交付与审核体验 | 另行批准任务集、版本、配置、次数及总预算后才执行；如实公布差异和限制 |

阶段 B 固定模型版本、推理设置、起始代码、任务材料、可用依赖、网络、缓存起点与预算。两组获得相同的交付目标和允许工具能力；基础 Pi 可正常使用其工具，不能刻意削弱。Keel 的流程编排、上下文整理、验收反馈和证据组织是待评测的处理差异，需完整披露；如 Keel 使用额外模型调用，其成本与时间一并计入。进一步去掉某项机制观察变化，可帮助定位贡献，但不要求第一轮就做大量组合实验。

阶段 C 固定任务与验收要求，向各工具提供等价的环境、任务信息和合理配置机会。记录 Agent、模型、版本、推理设置与可用工具；不同产品未必支持同一模型，所得是系统级比较，不能断言是 Keel 架构本身胜过另一模型。执行时间/费用上限及缓存状态尽量一致；无法统一的配额或计费方式必须说明，不能把订阅成本记为零。

比较前登记任务与排除规则，覆盖已声明的问题范围，保留失败，禁止事后挑选获胜案例。已知答案的开发案例用于调试，不作为未见任务能力的证明；正式比较保留未用于调试的任务，禁止一组看到另一组的结果或参考补丁。各组使用独立工作目录，平衡执行顺序；固定每个任务重复次数，任务内重试与独立重复分开统计。

少数案例只支持可行性或案例结论。对外报告成功数/分母、样本组成、重复次数、成本和不确定性；样本充分时使用适合按 Bug 分组的区间估计，不能把同一 Bug 多轮当成完全独立的大样本。未见稳定差异时直接说明，不把偶然领先写成普遍胜出。

## 5. 对外展示的边界

不需要所有指标都超过主流 Agent。可以证明在明确范围与预算内，交付率提高、人工救场更少，或理解更快且准确率没有实质下降；同时披露费用和速度的取舍。一个可重跑闭环、明确的工程机制、可信的对照和失败分析，比笼统宣称“全面超过 Codex/Claude Code”更有说服力。

当前优先完成阶段 A；阶段 B/C 和理解计时均为计划，没有新增实验授权，也没有已证明优于其他工具的结论。
