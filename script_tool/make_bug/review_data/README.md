# 复现评审开发材料 v1

关联 [Issue #14](https://github.com/elexcfe/keel/issues/14)。这一版补齐了现有材料能支持的 5 个开发切片、逐项参考标注、来源和排除理由。全部来自 **Actual #8351 一个 Issue**；没有完整准入正例，没有可用留出集，没有调用真实评审模型。

标注由当前 Codex 开发助手逐项阅读冻结原件后制作，与 Pi 产物、未来工作流评审输出分开。该助手了解之前讨论并实现过入口，**不是盲标，也没有经过人工或第二位标注者复核**；具体模型版本未采集。它们是冻结的 AI 参考标注，不冒充人工金标准。未将旧外层 verdict 直接当作答案依据；每项判断引用输入中可见的测试、声明、原日志或现存报告。

## 已交付文件

- [catalog.json](catalog.json)：5 个案例的源文件/归档成员摘要、Issue 分组、报告状态；其余 40 份现有格式运行记录逐项列为未选入或排除。选中与未选中集合合起来覆盖上次盘点的 45 份记录。
- [labels.json](labels.json)：评估侧参考标签、13 处可核对的文本引用、争议与不可推断事项，绑定每份 request 的 SHA256。不能发给被测评审者。
- [prepare.py](prepare.py)：仅按清单从原件复制字节，或在内存读取指定归档成员，然后调用既有只读入口。它不执行任何原脚本，不调用模型，不修改原报告，不重新生成 record，不覆盖已有输出。

`catalog.json` 和 `labels.json` 是开发者整理的评估资料，不是 Pi 报告。公开的是来源、摘要与参考标注；真实原视频、日志、源码副本只在本机忽略目录，不能宣称 GitHub 已托管完整评测集。

## 哪些案例能用

| --- | --- | --- | --- |

| case-102 | `run-20261019T162700-3l3v7evi` | 结构化结果全为 inconclusive，原始 reporter 却有 ASSERT PASS/FAIL；采集器读取的位置不对应 | 应指出记录不一致并退回；不能标成“所有断言实际都没执行” |

| case-104 | `run-20261019T114836-xoop2754` | 现存 initial/REPRO 引用此轮并列六条自动检查，record 实际只有四条；需区分观察与登记检查 | 应退回报告可追溯性问题；不据此否认分类现象或分类用例存在 |

每份输入包含原 Issue、冻结场景/测试、故障源码片段、登记证据和只读入口生成的检查摘要。case-104 另包含已存在的报告副本，**按原字节使用**；报告明确引用该轮，但不把“明确引用”当成报告生成时间已经证明，也不在本轮验证它的多轮稳定性声明。

case-103 当前 REPRO 确实存在并引用该轮，但同时写入前轮“被准入驳回”、纠正意见和答案。本轮将该报告整体排除，未删改后再伪装成原报告。因此这里的报告缺口部分来自主动防止答案泄漏，不应写成所有相关报告都不存在。case-101、102、105 没有可靠配对的历史报告，保持缺失，不从会话补写。

case-101/102/104 的主要发现是文本能够直接支持的错误；只说“缺报告/图片看不了”不算识别了这些语义问题。case-103/105 的首选是“无法判断”；明确说明缺口、请求补证据的“退回”也允许，但不得编造其他缺陷。逐项正例与整份复现通过是两个指标，不能混报。

## 不能用作什么

- 5 个切片属于同一 Issue，只能作开发与错误分析；不能把它们随机拆成开发/留出，也不能称为 5 个独立 Bug。
- **完整有效复现正例为 0**，不能估计对有效交付的错误驳回率。case-103 只有数值断言这一维度的正例。
- **现成留出 Issue 为 0**。Outline #13405 有旧 `summary.json` / `outcome.json` 和报告，本次补记了这 4 份旧运行的来源；此前“没有现有格式记录”不等于没有历史材料。但它缺少当前入口使用的 record、逐轮完整源码/场景归档与完整独立标注，保留为待整理来源，不能伪造 record 让它通过。
- `run-20261019T173608-7p1uoxax`、`run-20261019T175149-udpyx1un` 属于修复后运行/最终复验，不进入复现准入输入。其他未选轮次有同 Issue 重复、缺场景快照约定等具体原因，见 catalog。
- 图片/视频仅原样复制并校验摘要，当前文字入口没有观看能力。本轮没有新增画面编号、抽帧或时间校准，也不标注闪烁瞬间、截图内容正确性、视频时间准确性。
- 引用匹配检查证明“标注引用了这些原文”，不证明标注解释一定正确。争议维度和人工复核缺口保留，后续修改标签须增加版本，不在看过模型答案后悄悄改答案。

## 重建与核查

需要本机盘点中的原件，路径相对 `script_tool/make_bug`；源摘要不匹配即停止，保留部分输出用于诊断。使用全新目录：

```bash
python3 script_tool/make_bug/review_data/prepare.py \
  --out /absolute/path/new-review-dataset
python3 script_tool/make_bug/review_data/prepare.py \
  --out /absolute/path/new-review-dataset --check-labels
```

目录中：

- `inputs/case-NNN/`：原字节副本、原 record 和输入清单，只供准备程序读取。
- `requests/case-NNN/request.json`：**唯一允许交给未来无文件工具评审服务的输入**，不含 catalog、labels 或原 record.review。
- `requests/case-NNN/result.json`、`build.json`：评估侧机械校验、请求摘要和出处绑定；不作为答案提示发给模型。

标签仍留在本目录，不复制到 inputs/requests。当前入口不提供文件工具、shell 或真实服务适配；不能把这些目录交给拥有整个仓库读取权限的 Agent，然后声称答案已隔离。正文中的旧路径只是待审文本，不会被自动跟随读取。

本次本机派生包为 `script_tool/make_bug/output/review-dataset-v1-20261021/`。5 份请求均成功准备，181 份材料按摘要对应原件；13 处标签引用和输入摘要校验通过，整体机械检查仍为 incomplete，与报告/媒体缺口一致。

后续应先人工复核参考标注、准备无答案污染的完整正例与另一 Issue 的可用留出材料。历史缺件无法可靠找回就保持缺失或排除，不补写。真实模型调用继续等待模型、可发送材料、次数与费用预算明确。
