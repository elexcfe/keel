# Keel 产品说明

Keel 的目标是加快人与 AI 的协作效率：减少反复解释、等待和返工，让人容易理解改动、判断结果、推进工作。第一步从修 bug 做起，把问题复现、代码修复、运行验证和改动说明接成一个完整过程。

本文说明产品目标、使用方式和关键取舍。采用 DeepSeek Harness 插件的方向已经确定；商业化和效果预期仍需验证，不能当成已实现的能力。

## 1. 给谁用，解决什么问题

先面向中小型团队中经常使用 AI 编程工具、维护 Web 产品的工程师。他们能读懂代码，但仍要花精力核对 AI 的工作：背景有没有理解对，测试有没有真正运行，修改是否影响其他功能。

例如，AI 一次改了 15 个文件，开发者需要重新梳理这些修改之间的关系，才能判断它是在修登录问题，还是连支付逻辑也改了。问题在于理解整次改动的目的和影响，而不只是读懂某一行代码。

Keel 希望减少三类负担：

- **反复解释和准备。** 把问题描述、项目资料、日志和相关代码整理好，后续步骤能够继续使用。
- **反复催促和返工。** 主动运行检查，在交付前发现修复仍有问题，并继续纠正。
- **审核时重新摸索。** 说明改了什么、证据是什么、可能影响哪里，把需要人判断的地方讲清楚。

早期用“把 20 分钟的理解过程缩短到 20 秒”表达这个愿望。这是体验目标的举例，还没有测量结果支持。

## 2. 用户提供什么，拿到什么

用户提供 bug 描述、项目代码和可用的测试环境，按需要补充项目文档、日志、预期行为和测试数据。仅有一句报错通常不足以复现；Keel 应指出缺少什么，逐步减少需要人手工整理的材料。

可运行的环境和日志很重要，因为它们让 Keel 能观察问题、重跑同一检查，而不只根据代码猜测结果。早期设想直接连接网站和服务器；当前优先使用隔离的本地环境或已有测试站点。需要线上资料时，只在授权范围内读取，不修改生产数据。

一次修复应交付三样东西：

| 结果 | 用户用它判断什么 |
| --- | --- |
| 代码修改 | 具体改了哪里，是否接受这次修改 |
| 验证记录 | 原问题是否解决，相关测试结果怎样，哪些部分还没检查 |
| 改动说明和关系图 | 为什么这样改，可能影响哪里，哪里需要重点审核 |

验证记录包括修复前后的同一检查、相关测试结果，以及截图、日志或请求记录等佐证。关系图用于展示模块、函数或页面之间的联系；不能代替代码和测试结果。

## 3. 一次修复怎样进行

以“保存交易后，备注没有追加规则要求的文字”为例：

1. 用户提交问题、项目和测试环境，Keel 保存任务材料。
2. Keel 编写可重复运行的检查，在修复前多次观察到备注缺少文字。用户确认：“这就是我要修的问题。”
3. Keel 整理日志和相关代码，说明可能原因与准备修改的范围，用户确认定位方向。
4. Harness 的 AI 编码工具根据这些材料修改代码。
5. Keel 原样重跑已确认的检查，再运行相关测试。发现修复问题后继续修改和检查，保留每轮结果；无法继续时说明原因。
6. 用户查看代码、验证结果和改动说明，决定是否合入。

报告应先说结论，再给依据。例如：“备注现在能正确追加，原来的检查已通过。相关规则测试通过；其他页面尚未检查。这次还调整了规则执行顺序，需要重点审核其他规则是否受影响。”

复现、定位和合入是现有方案保留的三处人工确认。自动化负责推进工作，确认内容应帮助人作决定，避免让人重复核对已经提供的信息。理解说明要贯穿这些步骤，而不只是最后附一段摘要。

## 4. 为什么重点做验证和改动理解

**先复现，才有一致的修复标准。** 如果不知道怎样让问题出现，就难以判断一次修改是否解决了它。复现步骤还可以成为后续防止同类问题再次出现的测试。因此，先投入复现和验证，再逐步扩大自动定位与分析能力。

**截图需要检查结果支持。** 界面看起来正常，不代表保存的数据正确，也不代表其他功能没有受影响。Keel 必须同时提供目标问题的检查结果和相关测试结果。环境没启动、测试没运行、检查范围不足，都要如实说明。

**说明要建立在代码和执行记录上。** 先分析实际改动与代码关系，再让 AI 归纳和排序；对照修复前的计划，提示可能超出约定的变化。例如，原本只修登录，却同时改了计费模块，就需要解释两者的关系。多改一个文件不自动等于越界。

改动报告可以把“登录验证函数增加了参数，有一个调用位置可能漏改”放在前面，把单纯的引用路径调整合并到后面。这样，用户先看到可能影响行为的变化，仍能查看全部修改。具体分析步骤放在项目计划中。

代码生成使用现成工具，Keel 的主要投入放在复现、验证和解释上。原稿用“90% 精力”强调这个优先级，它不是已经核定的资源比例。

## 5. 第一版范围与取舍

| 选择 | 理由和边界 |
| --- | --- |
| TypeScript / React 项目 | 从一种技术栈开始，便于把浏览器行为与相关代码联系起来，避免同时解决多种语言的分析问题 |
| 有明确步骤的前端行为 bug | 可以检查文字、数值和交互结果，较容易建立修复前后的对照 |
| DeepSeek Harness 插件 | 复用已有编码能力和界面；Keel 的核心能力独立开发，减少重复建设 |
| 隔离的测试环境 | 允许反复准备数据、运行脚本和修改代码，不影响真实用户 |
| 先接受人工准备材料 | 先做完整的一次修复，再逐步减少人工定位和数据准备工作 |

第一版暂不处理后端、多语言、偶发竞态、依赖不可控外部服务或难以重建数据状态的问题。需要固定测试数据的简单问题仍可纳入，例如为备注规则准备几笔测试交易。

早期讨论过桌面视觉识别和语音讲解，目前不做。对于能从网页元素、组件信息或代码引用关系中找到的线索，优先直接读取这些资料；不增加一套通过截图猜代码位置的流程。语音也没有足够的用户需求依据支持优先投入。保留用图帮助理解的诉求，重点是展示代码关系和变化。

这些取舍用于控制第一版范围。后续是否增加能力，要根据真实任务的需要决定。

## 6. 风险与仍需验证的产品判断

首先要防止“看起来很可信，实际没有检查清楚”。测试通过只说明已检查范围内没有发现问题，不能承诺整个项目绝对正确。其次，报告如果提醒过多，用户会忽略它；遗漏重要影响也会损害信任。需要用真实任务逐步调整提示内容，并标明无法判断的部分。

用户是否愿意提供测试环境、材料准备是否太费力、三次确认是否值得，也是试点要回答的问题。工程上的风险和应对安排放在项目计划中。

Keel 与其他工具的关系，按协作需要考虑：

- 编程工具可以提供代码修改能力，也可能与 Keel 的部分能力重叠。
- 报错与日志工具可以成为问题来源；问题跟踪系统可以提供任务入口。
- 代码分析工具可以提供引用和依赖关系，Keel 再结合任务目的和执行记录解释变化。

原稿把验证与理解称为市场空白，把运行环境接入和计划对照称为竞争壁垒。这些都是早期假设，尚未完成市场调查。值得积累的是可复用的复现用例、可靠的运行记录和有依据的改动解释；是否能形成持续优势，要由实际使用证明。
