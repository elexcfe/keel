# 修复任务

你负责在同一个会话完成原因分析、代码修改、检查、根据反馈纠错和修复报告。不要在第一次修改后退出等待外层测试。复现已由外层审核，参考记录路径由 MAKE_BUG_REPAIR_REFERENCE 提供；先读取该记录、对应 result/runs/<baseline_run>/record.json、原问题 BUG.md 和 REPRO.md。不得调用 repair.py 为自己的复现准入或修改审核记录。

允许联网准备依赖和运行测试环境；禁止搜索修复答案、读取修复 PR/补丁、切换或拉取其他源码版本。不得触碰生产数据。

## 修改与验证

- 修改 repo/ 的业务代码并按需新增回归测试。先解释原因依据和修改范围；遇到需要改变已批准范围的情况，报告阻塞，不自行扩大。
- 保留已验收 scenario/ 及 manifest.files 所含断言、输入、数据恢复方式。不得放宽或删除检查以通过。确需改变验证方法时，记录原因，交回外层重新确认其在问题版本仍能复现。
- 可以用局部测试调试。准备交付时，通过 bash 执行 `bash run_scenario.sh`；执行器自动读取本次参考并给出检查摘要、运行编号及日志路径。正式验证保留 bash 默认 600 秒，不显式填写旧的 120 秒；场景默认 300 秒，--repeat 各轮共用该预算。必要回归属于已验收场景的 required_checks，其他局部测试不替代它们。
- `completed` 只表示执行完成；只有 repair.status=checks_passed 才表示本轮正式检查通过。失败时读取对应日志，预算允许就继续修改、调用同一执行器，不重新启动会话。缺项、未执行、环境阻塞必须如实区分，不能当目标失败或通过。
- 不修改原问题、历史记录、截图、视频和执行器。每轮保留原始材料。不要修改已验收运行的结果来对齐报告。

## 持续报告与交付

开始时用 write/edit 写 result/FIX.md，明确当前假设、已做修改和未解决问题；每轮正式验证结束后（包括失败和阻塞）先写当前结论、最新运行编号、证据位置、未确认项，再继续诊断或辅助分析。可以明确写“检查通过，视频尚未核对”，不能等证据分析全部完成或预算耗尽才更新。保留 REPRO.md。MONITOR.md 的阶段交付要求在修复任务中对应 FIX.md。

最终 FIX.md 写清触发方式、原因依据、修改文件与原因、为什么修复有效、修复前后运行编号与证据链接、必要回归结果、局限及人工帮助。引用本次最后一轮正式验证和参考运行的准确编号。瞬间 UI 异常可以视频为主，说明时间段和观察点，不把正常截图称为异常瞬间。

报告按“结论、原因、改动、前后证据、验证与限制”组织，同一事实只写一处。视频分析使用 `python3 video_evidence.py <视频> --at <相对秒数> ...`，先核对实际时长，通常只选 2–4 个关键观察点；单次最多 8 个、默认整次 60 秒。工具失败先报告缺口，不为派生图反复编写长时间分析脚本。请求时间不等于动作精确时刻，工具成功不代表画面已支持结论。收到纯文字纠正要求时用 read/edit/write 修改，确需新证据才运行相关命令。

检查通过后若再次修改源码，必须重新正式验证；写报告不应修改 repo/。预算不足、测试仍失败或准入条件失效时交付部分报告，不宣称修复成功。最终结论由独立验收者确认，你不能自授 accepted。
