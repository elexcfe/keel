# 最小修复闭环：缺口与实施方案

关联 [Issue #9](https://github.com/elexcfe/keel/issues/9)。本次是调查与实施方案，未实现以下新能力。场景交付依赖 #4，运行监测复用 #7，指标按 #8 对应的评测方案执行。当前不启动新的付费实验，不人工创建、补写或修改 Pi 的任务脚本、数据、报告及原始证据。

## 结论与起点

最小闭环是：**合格复现 → 冻结已验收条件 → Pi 修复 → 外层原样复验与回归 → Pi 说明交付 → 外层最终验收。** 先支持一个真实 Bug、一轮修复和明确失败退出，不先做自动多轮纠错、复杂关系图、平台或竞品比较。

Actual #8351 已证明 Pi 能从干净任务自行恢复依赖、观察异常、按时交齐文件；原样独立重跑也再次观察到 Bug。但本次交付仅部分通过，不能直接作为完整合格的修复输入。下一次真实运行前先补通用校验；实际场景缺项必须由 Pi 自己纠正并重新运行，不能由 Keel 开发者修补后计自主成功。优先沿用该问题和已保存材料，不要求无理由重做所有环境探索。若新场景改变断言或输入条件，须在原问题版本重新复现和验收。

## 1. 已有能力与缺口

| 环节 | 当前代码/事实 | 最小缺口及处理 |
| --- | --- | --- |
| 任务和环境准备 | make_bug.py 生成原始问题、源码、通用提示和运行器；依赖/工具清单及隔离副本已有 | 复用，明确准备材料是否人工提供，不能把目录隔离称为 OS 沙箱 |
| Pi 运行与预算 | run_pi.py 只有 single 或 prepare/reproduce；已有时限、费用、收尾、清理、会话统计 | 增加独立 repair 任务目的，不改变 single/split 的原含义；不能继续给修复阶段加载“只复现、不改业务”的提示 |
| 场景与证据 | run_scenario.py 保存场景/源码摘要、原始证据、执行状态；evidence.py 校验结构和证据文件 | 没有必需检查清单和稳定 ID，合法列表缺项也能通过；增加声明与逐轮结果对照 |
| 交付和复现准入 | delivery.py 检查五项文件、报告是否变化及链接；结论刻意仅为 files_present | 缺少选定轮次、必需检查与外层结论绑定的准入记录；不应把文件齐全直接作为修复入口 |
| 修复前后对照 | 每轮保存摘要，但只检查运行期间是否变化，不提供跨轮验收 | 冻结已验收参考轮次，修复后比对场景、数据条件、目标检查 ID；业务源码允许改变 |
| 回归与最终交付 | session_stats.py 的 review 只理解 reproduced/not_reproduced/blocked | 缺回归命令/结果和 repaired 交付口径；单独保存闭环记录，不改旧复现指标含义 |

Actual 暴露的具体问题：分类检查被后续列表赋值覆盖；manifest 仍称分类未覆盖、trace 未同步；报告把滚动前截图称为滚动后；挂载断言先失败导致后续滚动断言未执行；探索阶段使用共享 /tmp、setsid 并删除重建探索输出。正式场景已去掉 setsid，清理和最终原视频确有证据。**视频已证明瞬间消失，不要求补拍异常瞬间截图；问题是证据说明是否准确。**

## 2. 先补复现验收门槛

修改位置：resource/prompts/scenario.md、reproduce.md；src/evidence.py、delivery.py、run_scenario.py；test/test_scenario.py、test_delivery.py。不编辑本次 Actual 的 scenario/ 或 REPRO.md。

最小结构采用明确版本的新场景约定：Pi 在 manifest 中声明必需检查的稳定 ID、对应操作路径、正常预期及判定依据；每轮 checks 引用同一 ID，并记录 passed/failed/inconclusive 与原始证据。缺项、重复 ID、未声明 ID、空证据、版本不支持均提示不能准入；不靠模糊中文名称匹配。旧 schema:1 仍可读取/运行，但不能悄悄升级为新闭环合格输入。

这能发现“声明两条路径、结果只剩一条”，不能自动发现 Pi 从一开始就漏声明了 Issue 的必要路径。外层仍需对照原问题核查覆盖；报告自然语言与画面是否准确也需人工或独立评审，不声称用 JSON 校验解决所有语义问题。

Pi 必须区分“执行到并通过”“目标断言失败”“未执行/无法判断”。目标检查因失败中止后，后续检查不能凭默认值写成通过；可独立采集检查结果再汇总，保留原测试输出，具体实现由 Pi 决定。报告以最终引用轮次的检查结果为依据，清单与当前实现一致；瞬间异常标明视频为主、视频时间段和观察点，截图状态不得错述。

外层准入记录仅保存：参考 run ID、源码/场景摘要、已确认操作与必需检查 ID、数据恢复条件、reviewer、结论和证据链接。选定的是已独立验收的参考运行，不自动以第一次失败建立基线。未通过时停在 needs_reproduction_review；由 Pi 自行纠正后产生新轮次，旧材料保留。验收者可以写评审记录，不能写 Pi 任务产物。

## 3. 一次 Pi 修复与受保护复验

建议新增 src/run_repair.py 作为薄入口、resource/prompts/repair.md 作为修复要求；从 run_pi.py 提取可复用的模型启动、监测和清理逻辑，避免复制第二套预算执行器。同步 make_bug.py 的新任务生成与必要测试。初版只支持已符合新准入约定的任务，旧任务不自动覆盖迁移。

修复输入是原问题、合格场景/参考运行、当前源码以及经确认的修改范围和回归计划。Pi 提出原因和修改方案，外层保留项目既定的定位确认；若人额外提供解法，计人工救场。修复阶段允许改业务代码、增加回归测试，不允许改冻结的场景、目标断言、数据恢复方式或删除/放宽已有测试。新增文件也必须纳入差异审查。

参考证据与冻结清单保存于外层记录目录，修复副本只供 Pi 工作；每次复验前核对摘要。测试配置、依赖解析和辅助文件也可能影响检查，须审阅其差异，不能只检查测试主体。文件摘要和副本能发现意外变更，不是抵抗任意 shell 操作的安全沙箱。

状态尽量少：needs_reproduction_review → ready_for_repair → repairing → verifying → awaiting_review → accepted；任何阶段失败记录 blocked/failed 及原因。所有状态由外层入口写入，不由 Pi 自述推进。初版一轮修复失败即保存反馈并停住，暂不自动再次调用模型；保留以后恢复或自动纠错所需的轮次引用。

预算从准备修复输入、Pi 修复到复验和收尾共用一个 deadline 与费用账本，预留工具复验和报告整理时间，不为每条命令重新发放完整总时限。现有 run_scenario --timeout 是 check/run 各自上限，不能误当整轮总时限；闭环入口必须传递剩余时间并在顶层中断和清理。历史复现成本保留，与本次修复成本分列并汇总，不能从修复阶段重新计时后宣称全流程更快。

## 4. 回归、报告与最终验收

复用 run_scenario 执行已冻结场景，新增通用对照逻辑：前后场景摘要、检查 ID、数据恢复条件一致；修复前确认的目标失败在修复后转为通过，其他必需检查全部通过，无完整性或清理警告。没有可信的判定依据仍交由外层判断，不把执行退出 0 当修好。

Pi 在修复前根据改动范围提出必要回归命令、运行目录和判定标准，外层确认后冻结；外层执行并保存原始日志。已有失败需要修复前记录或可复核证据，无法区分新旧失败即不能通过。初版允许少量明确命令，不自动发现全项目测试或构建通用测试框架。

Pi 在看过复验和回归结果后产出独立的修复说明（例如 FIX.md），不覆盖 REPRO.md：触发方式、原因依据、修改位置、为什么有效、前后运行引用、回归结果和限制。同一受监测修复任务可安排“修改→工具复验→只读结果并写报告”的阶段；报告整理若需要再次调用模型，计入同一总预算，不冒充零成本步骤，且不得再改业务代码使验证失效。最终核对业务与场景摘要仍等于已验证版本。

外层另存一个闭环结果文件，引用已有 run.json、record.json 和评审，最少包含前后轮次、补丁摘要、回归结果、费用/耗时、人工介入及最终结论。指标聚合只读外层 accepted，旧复现 review 仍表示复现，不偷换为修复通过。初版保留人工/独立 AI 最终验收；不自动合并或部署，不先建设报告界面。

## 5. 实施顺序与离线验收

| 顺序 | 可检查的交付 | 不调用模型的验证方法 |
| --- | --- | --- |
| 1 | 必需检查 ID 与准入记录；Pi 提示同步 | 使用通用合成夹具：两条路径漏一条、重复 ID、未执行、假证据链接均不能准入；完整记录可准入；旧 schema 不误判 |
| 2 | repair 入口、独立提示、参考版本保护、共享预算 | 用假 Pi 验证修复阶段未加载“禁止业务修改”提示；场景或测试配置被改时拒绝验证；正常业务改动允许；超时/中断/费用耗尽保留记录并清理 |
| 3 | 前后目标检查对照、回归和结果交接 | 用小型合成项目验证失败→通过、目标仍失败、环境错误、回归新增失败、回归未执行、错误版本对照；均按真实状态退出 |
| 4 | Pi 报告要求和外层最终判定 | 假 Pi 模拟报告缺失、验后代码变更、人工救场和完整交付；仅合格且未救场计自主 accepted，失败不自动重试 |

测试夹具是通用工具的测试输入，不是手工补写 Actual 场景，也不能计 Pi 独立成功。既有进程清理、证据快照和监测测试复用；仅在新增行为需要时增加回归，不重做已验证能力。探索目录约束继续通过任务内 TMPDIR、轮次归档和提示加强，任意 shell 的硬隔离另行评估，不把建设完整沙箱作为首个闭环前置条件；越界行为照实记录。

完成上述离线实现后，才有条件安排一次另行授权的 Actual 真实修复验证：先由 Pi 补齐自身复现交付并在问题版本确认，再修复、同场景复验、回归和交付。不得直接使用人工诊断场景或现成修复替 Pi 完成任务。若预算不足或准入未通过，记录阻塞并结束，不自行追加付费运行。
