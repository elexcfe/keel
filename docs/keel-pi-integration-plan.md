# Keel：Pi 接入方案

> 初稿：2026-10-12；方向更新：2026-10-21。
> 状态：Pi 仍是当前执行主体；下一项为只读复现评审回放，尚未实现自动评审或反馈。本文说明接入边界与后续安排。
> 产品目标与范围看产品说明，整体实施与验收看项目计划。关于 Agent 运行形式和接入方式，以本文为准。

## 1. 为什么改用 Pi

Keel 需要一个能读项目、执行命令、修改代码并保留会话的 Agent。我们不准备再造这部分能力，而是在现成 Agent 上完成问题复现、修复验证和改动解释。

选择 Pi，主要基于三点：

- **核心精简。** Pi 把基础 Agent 循环和少量工具放在核心中，Keel 可以只加入当前需要的流程，不必接受一整套预设工作方式。
- **扩展入口完整。** 简单任务可以直接使用 Markdown 任务材料和命令行；需要更深接入时，可以增加提示模板、技能、TypeScript 扩展、JSON/RPC 进程接口，或用 SDK 嵌入应用。
- **已有实际基础。** 仓库里的 `make_bug` 已经按 Pi 的命令行方式生成任务、准备环境、保存复现结果，并提供独立验证入口。总体方案继续沿这条路径发展，减少重复建设。

当前选择主要基于已有实现和接入成本；使用体验不构成相对 Codex、Claude Code 或其他方案的稳定性和收益证明。我们仍固定经过检查的版本，保留升级前后的回归检查。

原 DeepSeek Harness 方案由本文替代。原方案中复现、验证、定位、审核等职责继续保留；改变的是这些能力如何接入 Agent。

## 2. Pi 和 Keel 各自负责什么

Pi 负责通用的 Agent 工作：阅读项目、分析问题、调用文件和命令工具、修改代码、维持会话，以及按任务要求生成结果。

Keel 负责修复过程中的专门约束和证据：

| Keel 的职责 | 要交付的结果 |
| --- | --- |
| 流程与审核 | 当前进度、人工确认、失败原因和最终结果 |
| 复现与验证 | 固定复现包、修复前后结果、相关测试、截图和日志 |
| 定位与修复上下文 | 问题材料、可能原因、相关代码、准备修改的范围 |
| 改动理解 | 行为变化、可能影响、超出约定的变化和审核重点 |

这里的“复现与验证”是 Keel 对流程结果的责任，不表示由开发 Keel 的 AI 手写每个 Issue 的场景。具体场景脚本、测试数据及恢复方法、观察与断言逻辑、截图/视频采集和复现报告由 Pi 产出；Keel 提供通用运行约束与检查，人或独立验收 AI 重跑并核对证据。验收者发现缺失或错误，应记录部分完成/受阻，改进通用提示、生成或校验逻辑，再由 Pi 重新产出，不能补写某次产物后算作 Pi 成功。

人工介入产生的场景只能另作诊断，明确来源，不能纳入 Pi 独立产出的成功率，也不能作为新一轮能力验证的预置答案。原始产物和失败记录保留，外层评审另行记录，不覆盖 Pi 报告。

这是业务职责的划分，不等于必须开发四个 Pi 扩展。第一版优先使用任务文件、普通程序和运行脚本。只有需要直接参与 Pi 会话或界面时，才做扩展。

Keel 的核心检查要能脱离 Pi 独立运行。例如，Pi 生成场景后，由 `run_scenario.sh` 独立重跑并保留行为证据、自动检查结果和代码快照，不需要再次询问 Pi。执行完成不等于已复现或修好，结论由人或 AI 引用证据评审。

下一项 [复现评审回放原型](../plans/reproduction-review-replay.md) 把外层的复现审核作为可测对象：只读冻结材料、输出建议及依据，不重跑场景、不自动准入、不写 Pi 产物。先检验错误放行、错误驳回和无法判断，再决定是否接入反馈。评审 Agent 是工作流参与者，不能兼任证明整个系统有效的最终裁判。

## 3. 分几层接入 Pi

按需求从轻到重选择接入方式，当前层能解决问题时，不提前进入下一层。

### 第一层：任务材料和命令行

用 Markdown 说明问题、环境约束和交付要求，用脚本准备依赖、启动 Pi、保存日志并运行验证。Pi 仍是正常的终端 Agent，Keel 通过明确输入和文件结果控制流程。

现有 `make_bug` 已经实现这条路径：

1. 从 GitHub Issue 准备问题原文和指定代码版本。
2. 生成 Pi 的任务要求、环境恢复要求和场景交付要求。
3. 启动前准备项目依赖和工具；失败时把真实日志交给 Pi 诊断。
4. 要求 Pi 建立可重跑场景并采集证据，不在复现阶段修改业务代码。
5. 用独立的 `run_scenario.sh` 重跑场景，分开记录执行状态、观察事实和自动检查，并保留原始证据。

这条路径已经证明文件化交接可行。最小修复接入沿用 run_pi 的单会话与 bash 工具：Pi 调用现有执行器，读取结果后继续修改或交付报告。Actual 的两条已声明路径已经在外层反馈后通过修复验收；不是首次交付或无人工反馈的自动成功。最新报告提醒、过期检测和限时视频工具已有离线测试，真实 Pi 的效率改善仍待验证；具体记录见 [修复闭环计划](../plans/repair-loop.md)。

### 第二层：Pi 包中的提示、技能和扩展

重复使用的提示可以整理成提示模板；需要按场景加载的工作方法可以整理成技能；需要监听会话事件、拦截工具调用、增加命令、工具或界面的能力，再写 TypeScript 扩展。

可能需要扩展的场景包括：

- 在执行前展示复现、定位或合入确认。
- 记录 Pi 准备做什么、实际调用了什么工具，并与最终修改对照。
- 在会话中展示任务状态、验证结果和需要用户处理的阻塞。
- 限制修改范围，保护固定复现包和敏感路径。

这些资源可以打包成项目级 Pi 包，固定版本并随 Keel 一起检查。第三方包在加载前要审查，因为扩展代码能够执行程序。

### 第三层：JSON/RPC 或 SDK

当 Keel 需要在自己的界面中持续控制 Agent、接收结构化事件或管理长会话时，再评估 Pi 的 JSON/RPC 模式。Node.js 或 TypeScript 应用需要直接控制模型、会话、工具和资源加载时，可以使用 Pi SDK。

这一层会增加进程管理、错误恢复、接口兼容和凭据处理成本。第一版没有这些需求，不为将来的界面提前嵌入 SDK。

### 按需求接入其他编码工具

若后续用户需要在 Codex 或 Claude Code 中使用，可由薄 Skill 引导调用同一套 CLI，CI 复用必要检查。Skill 可以携带脚本，因此它与独立维护验证工具不冲突；独立仓库不要求独立客户端。当前没有实现这些接入，也不为比较或增加 Agent 标签先建设多套适配器。

## 4. 一次修复怎样完成

以“保存交易后，备注没有追加规则要求的文字”为例：

1. Keel 保存问题、代码版本和环境信息，生成 Pi 可读的任务材料。
2. Pi 在隔离环境中建立复现脚本。执行器保留目标问题的观察与记录；有稳定性疑问时再安排必要重复。
3. 当前由外层审核者显式确认复现正确；Keel 选定经过评审的参考运行和预期结果；修复使用固定场景；若改变断言或数据条件，须在问题版本重新复现并验收。下一项回放的模型建议不会替代这道准入。
4. Pi 根据问题、日志和相关代码提出修复方向。需要时让用户确认范围。
5. Pi 修改业务代码，但不能修改已经固定的断言来获取通过。
6. Pi 在同一会话内通过 bash 调用现有执行器，原样运行参考场景及必要回归。结果直接作为工具输出返回；失败后预算允许就继续修改，不退出并重启 Pi，保留每一轮记录。
7. Pi 在同一会话产出 FIX.md，解释原因、修改和前后证据；Keel 核对最终代码与验证版本、报告引用和必需检查，外层审核内容是否成立。代码关系分析属于后续增强。
8. 用户查看代码、证据和未覆盖范围，决定是否合入。

Pi 会话正常结束只表示 Agent 停止运行，不表示问题已经复现或修好。正式检查通过后仍需独立验收覆盖、解释和行为证据，不能仅凭结构化结果宣布交付成功。

## 5. 模块之间怎样交接

每份结果都要标明任务、运行轮次和代码版本；存在未提交修改时，还要记录修改内容，不能只保存提交号。

模块通过固定文件和字段交接，不从聊天文字中猜状态。例如：

- 复现结果包含检查步骤、预期行为、实际行为、结果状态和证据路径。
- 修复输入包含固定复现包、相关日志、代码位置和已确认范围。
- 运行记录区分执行完成、环境阻塞、执行错误和中断；观察、自动检查结果与评审结论分别保存，列出证据与未覆盖范围。
- 改动说明引用实际 diff、工具记录和代码关系；无法确认的影响标为不确定。

场景执行不依赖失败基线，不自动安装依赖。每轮保存场景文件及源码快照（含未忽略的新增文件）、视频/截图/事件等原始材料和可读报告。证据缺失或执行期间代码变化明确提示；人或 AI 在独立评审中引用运行和具体证据，不能覆盖原始记录。修复模式对照已验收参考与当前运行；仍不自动完成视频或报告语义评审。

字段变化需要标明格式版本。Pi 扩展、普通脚本和以后可能出现的界面都读取同一种结果格式，避免把业务状态绑在某个 UI 或单次会话中。

## 6. 会话、版本和安全边界

开发阶段保留 Pi 会话，便于回看推理上下文和工具调用。自动流程通过 run_pi.py 默认监测，single/split 每阶段使用独立 session-dir，保存会话、提示、状态与可重算统计；默认启动新会话；是否恢复旧会话必须明确指定，避免把其他任务的答案或状态带进来。

Pi、Keel 的 Pi 包和任务结果格式都要固定经过验证的版本。升级时用代表性任务检查启动参数、扩展加载、会话保存、工具调用和验证结果，不能只确认 Pi 能启动。

Pi 的扩展能力强，也意味着扩展可以执行代码。项目级包和外部包要先审查来源与权限。任务仍在隔离的本地环境或测试站点执行，不写生产数据；工具列表和提示约束不能被描述成操作系统级沙箱。

## 7. 开发顺序

现有同会话修复、[任务入口](../plans/task-lifecycle.md) 与 [交付入口](../plans/task-handoff.md) 继续复用。下一阶段按以下顺序推进，具体实施以项目计划和对应 Issue 为准：

1. **复现评审回放。** 通过独立入口读取允许访问的冻结材料，先做机械检查，再输出模型建议；标签、旧外层结论和修复答案对评审不可见。只保存新评审记录，不调用正式准入、不启动新的执行者会话。
2. **有限自动反馈。** 回放质量达到预先规定的要求后，再考虑在 `task_flow.py` 的复现准入和最终交付位置接入评审调用。先只设执行者、评审者两个角色；退回内容由 Pi 自行处理，调用轮数、耗时和费用共用已授权预算。无法判断和失败明确交接。
3. **原始 Issue 完整对照。** 两组自行生成复现和断言，使用相同任务条件和资源约定；隐藏验收只在结束后使用。现版依赖外层准入的限制须如实计入，不能由实验偷偷签发通过。预审基线试验只能证明修复阶段效果。
4. **按需 Skill/CI 接入。** 根据使用需求包装已有工具，不预先建设独立客户端、RPC 平台或更多角色。

模型建议、机械检查和正式审核决定分开记录。未来若委托模型作某类准入判断，须明确验证范围、来源和抽检政策；两个 Agent 一致同意不代表独立证实。强评审也可能共同误解原问题，自动通过样本必须纳入检查。

评测同时比较较便宜执行模型加较强评审与单强模型，并计入失败重试、人工处理、持续抽检和维护成本；只有对照支持时才声明收益。复杂代码关系图、更多语言、视频加工和通用自动恢复后置。本次只更新文档和登记下一项任务，不写代码、不启动模型调用或实验。

## 8. 风险和验证事项

| 风险 | 当前处理方式 |
| --- | --- |
| Pi 升级改变命令、扩展或会话行为 | 固定版本，集中维护启动和扩展入口，用真实任务做升级检查 |
| 会话内容被当成正式证据 | 通过固定复现包和独立验证结果得出结论，会话只作为过程记录 |
| 扩展过多，使原本精简的方案重新变重 | 能用任务文件和脚本解决时不写扩展；每个扩展对应明确需求 |
| 第三方 Pi 包执行未审查代码 | 默认不加载；项目包固定来源和版本，启用前审查 |
| 拿不到足够完整的计划或工具记录 | 在代表性任务上验证 Pi 事件；缺失信息如实标注，不宣称完成计划对照 |
| 评审与执行者共同接受错误结论 | 保留独立原问题视角、证据引用、通过样本抽检和隔离的终局评测，不以共识判真 |
| 评审泄漏答案或反复调用增加成本 | 限制输入可见范围，记录模型/提示版本和全部用量；先回放，再决定反馈范围与预算 |
| 总体文档与实际脚本再次分叉 | 接口和路径变更时同步资料索引与本方案；具体命令以工具说明为准 |

当前还要通过实际开发回答：哪些确认必须在 Pi 会话内完成，哪些只需外部脚本；扩展事件能否稳定提供计划对照所需的信息；失败重试和中断恢复怎样与 Pi 会话配合。
