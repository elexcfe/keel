# 固化复现与修复后验证

首次探索完成后，必须留下无需再次调用 pi 的复现包。只新增测试、运行配置和辅助脚本，不修复业务代码。`verify.sh` / `verify.py` 是工作流提供的统一入口，不修改它们来改变结果。

## 交付接口

在 task/repro/ 创建以下文件，路径从 `MAKE_BUG_TASK` 推导，不写死机器路径：

- `manifest.json`：`{"schema":1,"coverage":["实际覆盖的症状"],"files":["repo/相对测试路径","repro/其他辅助脚本"]}`。files 必须列全测试、加载的测试配置及自定义辅助脚本；run.sh、check.sh、env.sh、manifest.json 自动加入校验。不要把业务实现放进 files。报告说明未覆盖症状。
- `env.sh`：只导出执行必需环境变量。启动器已经提供共享浏览器路径、MAKE_BUG_TASK、MAKE_BUG_TASK_TOOLS、MAKE_BUG_RUN_DIR、MAKE_BUG_OUTCOME。不要下载、启动后台服务或修改代码。
- `check.sh`：只做环境检查，如本地依赖加载、所需库存在、浏览器实际启动。缺失时打印准确原因并非零退出，不自动安装。非 Node 项目也必须检查自己的运行环境。
- `run.sh`：初始化独立合成数据、执行固定测试，并保存结构化结果。不得联网搜索、下载依赖、修改测试或业务代码。需要构建时正常构建，不使用旧构建判断新代码。

测试结束必须向 `$MAKE_BUG_OUTCOME` 写 JSON：`{"status":"passed|target_failed|blocked","reason":"实际判断依据"}`，退出码分别为 0、1、2。只有测试框架结构化结果中指定的目标断言失败才能写 target_failed；启动失败、超时、选择器失效、语法错误、未发现测试等全部为 blocked。不能仅用命令非零退出分类。无可靠自动判定时如实交付人工限制，不伪造可自动执行的结果。

日志、截图、trace、框架报告统一写入 `$MAKE_BUG_RUN_DIR/logs` 或 `images`。不覆盖旧 result/REPRO.md 和基线证据，不把浏览器用户数据写进结果目录。REPRO.md 使用相对链接指向 runs/ 下的实际证据。

## 服务与测试可靠性

- 使用任务专属端口，检查占用时明确停止，不复用来源不明的服务。由测试框架或脚本启动当前 repo 的服务并等待就绪；保留启动日志。清理只针对自己启动的进程，不用 pkill 或按端口杀进程，不使用 nohup/setsid 脱离验证进程组。
- 每次使用独立浏览器上下文和相同数据起点，清理本次资源。断言正常行为，目标 Bug 存在时失败。
- 不用固定 sleep 代替业务完成条件。观察从操作前开始，等待相关计算结果更新等可确认的完成条件。不得要求错误必须发生才能结束等待，否则修复后会变成超时。
- 对 Issue 的每个症状明确覆盖范围。滚动问题应设置实际滚动容器并测量滚动位置；DOM 卸载可以作为辅助证据，不能代替用户行为判定。

## 固化与验收

1. 完成脚本后，从 task 执行 `bash verify.sh --baseline --repeat 3`。有 Bug 基线必须实际触发目标断言；不能把环境失败当基线。若偶发或不足三次，在报告中明确说明。
2. 首次目标断言失败后自动写 repro/baseline.json，记录测试文件和依赖指纹。此后不修改该复现包；若探索阶段确实需要改测试，先把整份 repro 和基线证据备份到任务 tools/tmp 下，明确记录原因，再建立新基线，不悄悄绕过检查。
3. 修复后用户运行 `bash verify.sh`，保持相同断言；不需要再调用 pi。依赖输入发生变化时默认停止，经确认执行 `bash verify.sh --prepare`；该选项允许运行安装，npm ci 会重建 node_modules。
4. 已有安装钩子的项目默认保守检查源码。只有查清安装脚本依赖哪些文件后，才可在 deps-config.json 的 dependency_inputs 中声明仓库内相对 glob 列表，清单与锁文件仍自动检查。不要为了跳过检查填写空列表；本地 file/link 依赖自动纳入检查。
5. REPRO.md 给出唯一验证命令、环境需求、每次结果路径和覆盖限制。一次通过只代表已覆盖场景通过，不代表整个 Issue 已完全修复。
