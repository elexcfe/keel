# 代码仓知识沉淀与相关 Bug 检索

状态：增强能力构想，待核心能力完成后推进，本文仅做记录。

## 背景与目标

系统初次接触用户代码仓时，缺少需求背景和历史修复经验。新需求可能引入 Bug，修复 Bug 也可能引入新的问题；不了解这些历史，容易反复猜测、重复定位和返工。

目标是让系统在同一代码仓中积累经验，后续任务能参考已有需求和相关 Bug 的解决过程。

## 能力思路

- 沉淀需求背景、业务约束，以及 Bug 的触发条件、根因、修复方式和回归测试。
- 关联需求、代码变更、引入的 Bug 与后续修复，保留来源和适用版本，避免旧结论误导新任务。
- 处理新 Bug 前检索相关历史，优先参考同根因、同业务约束、同调用链或由历史修复引发的问题，不只匹配关键词。
- 例如：解决 Bug A 后保存修复经验；遇到高度相关的 Bug B 时，利用 A 的证据缩小定位范围，再通过复现与测试验证。

核心能力阶段可先保留任务记录，后续再建设知识整理与检索能力。

## 验证思路

从现成 GitHub 开源仓库中挑选有关联的 Bug，按时间顺序处理，比较使用与不使用历史记忆的效果。处理后续 Bug 时，只使用当时已有的信息，避免提前读取其修复答案；同时保留无关联或表面相似但根因不同的样本。

- **相关 Bug 检索命中率**：存在已标注相关历史 Bug 的任务中，前 K 条检索结果至少命中一条的任务占比，固定 K 后比较。
- **定位效率**：定位根因前的耗时、工具调用次数。
- **修复效果**：修复尝试次数、人工返工次数、回归测试结果和修复成功率。

检索命中是过程指标，最终要验证是否减少猜测和返工、提高修复效率。
