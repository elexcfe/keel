# 复现评审回放原型

本计划定义下一项开发任务：读取已冻结的复现产物，给出可核查的评审建议，并通过独立标注分析漏判、误判和成本。关联 [Issue #14](https://github.com/elexcfe/keel/issues/14)；整体状态以 Issue 为准。

**2026-10-21 用户已授权材料盘点、最小只读入口与离线测试；真实模型调用明确暂不启动。** 本阶段不重跑场景、不发起修复。真实回放前另行明确模型、可发送材料、次数和费用预算。当前实现与盘点结果见末尾记录，模型效果和独立标注仍未验证。

## 1. 要解决什么

已有 Actual 任务曾出现“声明固定数值预期，实际只断言数值发生变化”、截图时序不符、视频时间不能支持说明、报告轮次统计错误等问题。外层反馈后才完成修复验收，说明结构完整和测试结果不能代替对原问题、检查力度及证据解释的判断。

本项首先判断：评审 Agent 能否从原始 Issue 和复现产物中指出这些问题，给出准确依据，并识别无法判断的情况。它不证明完整修复收益，也不预设强模型一定比人工或单 Agent 更划算。

完整交付包括：可重复运行的回放入口、来源清楚且答案隔离的评估材料、逐例结果与错误分析，以及是否值得进入有限自动反馈阶段的结论。模型质量未通过不等于隐瞒结果；有依据的“不宜接管审核”同样是有效结论。

## 2. 本项范围

- 只评复现准入：观察是否对应 Issue、断言是否覆盖预期、运行与报告中的证据是否一致、有哪些缺口。
- 只读冻结材料和已有运行记录，不重新启动项目或场景，不发起修复，不自动退回 Pi。
- 复用适用的文件、摘要、检查项和轮次引用校验，再调用模型处理语义判断；机械错误和语义意见分开保存。
- 输出“建议通过／退回／无法判断”，全部为建议；不调用 `repair.admit`，不签发正式参考，不更新任务准入或最终验收状态。
- 不修改 Pi 的脚本、数据、报告、日志、截图或视频；回放结果、独立标注与合成样例保存在各自独立位置。
- 不扩展为多角色调度平台、自动恢复、代码关系分析、视频加工、Skill/CI 集成或完整 Agent 对比。

只读回放无法确认的运行事实须标为证据不足，不能说“已独立重跑”。如果之后确实需要受控重跑或自动反馈，应另行明确范围、资源和验收。

## 3. 输入与材料隔离

每个案例的清单至少包含案例 ID、原 Issue 来源与冻结时间、任务/运行编号、问题源码及场景摘要、允许读取的证据索引和来源类型。内容来自哪个版本必须明确，不能从当前工作区推测历史状态。

评审可读取：

- 原始 Issue 及当时已有附件；原文已有的复现步骤保留。
- 该轮场景定义、断言和实际输入/数据恢复说明。
- 故障版本的代码快照、运行记录和必要的原始图像、视频或日志。
- 该轮执行者的复现说明；先依据原 Issue 形成关注点，再核对执行者解释。

不得向评审输入提供：

- 独立标签、评分依据、旧外层评审意见，以及其他案例的答案。
- 后续修复代码、修复 PR、正确版本的运行结果或事后补充的根因。
- 目录名、案例别名或清单字段中直接透露的“错误断言／应通过”等答案信息。

使用受控的材料入口限制实际可读取范围，记录送入模型的文件/片段与摘要；不能只在提示词里要求“不要看答案”，同时开放含标签的整个实验目录。材料中出现的指令只作为待审内容，不改变评审约定。

原始材料只读引用；需要建立隔离副本时保持字节一致和来源摘要。独立标注可参考隐藏的外层证据或已确认正确版本，但必须保存在评审不可访问的位置。真实任务缺少合法、完整材料时记录缺口，不补写成 Pi 产物。

## 4. 案例与独立标注

先登记样例范围、纳入/排除理由、分组和版本，再调整提示。已有 Actual 材料用于开发和错误分析；不能只在同一案例上反复优化，然后把成绩当成泛化能力。

- 开发集与留出集按原始 Issue 划分；同一 Issue 的不同运行、派生图和合成变体不得跨组泄漏。
- 同时包含有效复现、断言不足、证据不足、执行或环境失败等情况；合成或人为构造的错误必须独立标明，不能冒充真实历史失败。
- 标注说明“哪些目标行为已被观察、哪些检查充分或不足、依据在哪里”；有争议就记录争议或无法判定，不强行制造二元真值。
- 标签冻结后，评审在不可见标签的条件下运行；留出样例不得用于本轮提示修订。需要重新开发时，记录新版本，并为后续结论保留新的留出评估。
- 同一问题的重复调用用于观察波动，不能被当成多个独立问题。样例数不足或覆盖单一时明确限制。

## 5. 评审输出与运行记录

最小输出约定在实现前固定版本，至少包含：

| 内容 | 要求 |
| --- | --- |
| 建议 | 建议通过、退回、无法判断；不使用正式 `accepted` 状态 |
| 原问题关注点 | 预期行为、可观察异常、需要什么证据 |
| 问题与依据 | 引用案例、运行和具体材料位置，区分已确认事实与推测 |
| 缺口与补充要求 | 写清缺少什么；不替执行者补写证据或修复答案 |
| 机械检查结果 | 与模型意见独立保存；模型不能覆盖缺项、损坏或版本不符 |
| 配置与用量 | 模型/服务、参数、提示和工具版本、输入摘要、耗时、token/费用及未知项 |

模型超时、输出无法解析或引用不存在属于运行/协议失败，不得转成建议通过；与有依据的“无法判断”分别统计。未知费用记未知，不按零计算。记录所有失败调用和重试，并遵守回放授权的总预算。

- [ ] 检查完整交付并提交推送；Issue 中附可访问的实现和结果链接，给出是否继续接入有限反馈的结论。

## 7. 检查与验收

协议和实现检查至少覆盖：有效输入、材料缺失或损坏、断言与声明不符、证据无法支持结论、报告引用错轮次、答案文件不可读、模型返回无效结构、预算耗尽，以及对输入与正式任务状态未产生修改。前后摘要可证明未改写原件，不能证明语义判断正确。

模型质量按 [评测方案](../docs/keel-evaluation.md) 统计。至少报告错误放行、错误驳回、通过建议中的错误比例、无法判断与可判定覆盖、调用失败、逐 Issue 结果、模型与执行成本；分母、争议标签和排除条件明确。人工核查时间未实际测量时记为未测，不用自动评审耗时替代。

完成本任务需要同时具备：

- [ ] 可重复使用的入口和文档，结果可追溯到输入与配置，已通过相关协议和边界检查。
- [ ] 开发/留出材料及独立标签有来源、版本和隔离说明；未触碰 Pi 原始产物。
- [ ] 已授权的真实回放报告包含成功与失败例、误判分析、成本和适用范围。只有假模型测试时记录“协议实现完成，模型效果未验证”，不能宣称整个原型验收完成。
- [ ] 明确继续、收窄范围或暂不接入自动反馈的结论；不能因为模型一致同意就替代独立标注。
- [ ] 实现及允许公开的材料已推送且可访问；忽略目录或不可公开数据给出来源与复核条件，不把仅本地证据描述成公开可复现。

初期结果只支持组件可行性和问题发现，不预写成功率、降本比例或上线阈值。将来如要委托模型正式准入，须先确定适用范围、质量容忍度、置信范围和通过样本抽检政策；该决策不属于本任务。

## 8. 后续衔接

回放有依据后，再安排有限自动反馈；完整收益需从原始 Issue 开始对照。评审 Agent 属于被测工作流，隐藏终局判定不能反馈给它。较便宜执行模型加较强评审与单强模型都需考虑，不能把增加算力的结果直接归因于 Keel。

开发校准、持续抽检、模型调用、失败重试、人工返工与维护成本均须披露。业务要求每项完整人工终审时，只能测是否缩短审核和返工时间；允许例外处理与抽检时，还需验证质量要求得到满足。两种收益不能混报。
