# 最小修复闭环：同一会话完成修改、检查、纠错和报告

关联 [Issue #9](https://github.com/elexcfe/keel/issues/9)。本计划替代此前的“一轮修复退出后复验、再启动报告阶段”设计。当前授权范围是通用实现与离线测试，不启动新的付费实验，不人工补写 Pi 的场景、数据、脚本、报告或原始证据。

## 目标与分工

调用链：已验收复现 → run_pi 启动一个修复会话 → Pi 修改代码 → Pi 用 bash 调用 run_scenario → 结果回到原会话 → Pi 继续修改或写 FIX.md → 外层核查并独立验收。

Pi 自主分析、修改、调试并产出报告；Keel 执行确定性的记录和校验。验证不会终止或重启 Pi，不增加专用 verify_repair 工具、第二套模型启动器或自动恢复状态机。单次任务允许总预算内多轮修改；不自动追加会话或预算。动态时间/token 注入留在 Issue #10。

Actual #8351 当前只有部分通过的复现交付。分类检查遗漏、场景说明和报告不一致须由 Pi 自行纠正并重跑，再经独立验收后进入修复。瞬间消失可用视频证明，报告要说明视频时间段和观察点，不强求截图抓到瞬间。

## 最小技术方案

1. **明确检查约定。** 场景 schema 2 声明必需检查的稳定 ID、正常预期及 target/regression 类型；结果逐项引用 ID。漏项、重复、未声明、未执行、无有效证据不能通过。schema 1 保持可读取和运行，但不能作为修复准入材料。结构校验不能发现从一开始就漏声明的 Issue 路径，仍由独立验收确认覆盖。
2. **记录复现准入。** 外层审核后显式选定参考运行，保存 reviewer、审阅依据及参考记录摘要。要求目标确实失败、必要回归通过、原始证据齐备；不把第一次失败自动当基线。复用已有源码和场景快照，固定原问题、操作、数据恢复条件和断言。摘要用于发现意外变化，不宣称能抵抗同权限 shell 篡改。
3. **扩展现有执行器。** run_scenario 复用执行、归档和清理，支持与准入参考对照并返回简明检查摘要。执行成功与检查通过分开；环境失败、检查遗漏、目标/回归失败有明确反馈。原场景中包含预先确认的必要回归，不另造回归调度框架；Pi 可另跑局部测试，但不能替代正式必需检查。改变参考场景须回到旧版本重新确认。
4. **增加修复任务目的。** run_pi 选择修复提示，保留一个 Pi 进程和会话，不加载禁止修改业务的复现提示。先确认当前源码和场景仍对应准入参考，再启动；向执行器传递参考路径和剩余总时限。准备、修改、检查、收尾共用现有 deadline 和费用账本，场景子阶段不能各自重新获得完整总预算。
5. **核对交付。** Pi 在原会话中写 FIX.md 并引用前后运行编号。Keel 记录候选结果：参考运行、最终运行、代码摘要、检查、报告及人工介入声明；只有最终源码与合格运行一致、必需检查齐全且通过、报告存在并引用正确运行，才进入 awaiting_review。报告原因是否成立、画面是否支持文字、Issue 覆盖是否完整仍由外层验收；不自动记 accepted，不改旧复现指标含义。

报告应解释触发方式、原因依据、代码改动、为什么有效、前后证据、回归与限制。Keel 生成执行事实和核查结果，不代写上述分析。报告更新保留检查点，预算不足时如实交付部分结果。

## 独立验收与范围

调试时不重复运行相同命令，Pi 可以先做局部检查，再运行完整场景。交付时审核版本、记录、代码和证据；Actual 的 UI 时序问题在后续获准真实运行时安排一次最终独立复验。不能因为 JSON 完整就省略语义验收，也不要求每轮 Pi 跑完再由 Keel 重跑一次。

必要回归先限定为少量明确检查，并纳入参考场景。新增回归测试允许，但不能放宽已验收断言；配置、依赖和测试辅助文件的变更仍要审查。初版不解决任意 shell 的强安全隔离，不增加 SDK/RPC、跨会话恢复、多 Agent 审核、自动合并或报告界面。
