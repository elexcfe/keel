# Keel 项目计划

围绕“端到端修复交付率”和“帮助人快速、准确理解 Bug 与修改”，先完成一个真实 bug 的复现、修复和验证，同时交付基本说明；再减少人工准备工作，逐步补齐改动分析。每一步都要留下可检查的结果，不能只以“代码写完了”判断完成。

本文保留实现思路、阶段安排、验收、风险和待决问题。当前采用 Pi 作为运行与编码主体，接入细节以 Pi 接入方案为准；早期的工期和验收数字在文末保留为草案，不作为当前承诺。这里描述开发安排，不代表相应能力已经实现。

## 当前实施优先级

已有依赖清单、场景执行、同会话修复、监测和报告检查继续复用；Actual 的两条已声明路径已经在外层反馈后完成修复验收，不代表首次交付或无人工反馈成功。下一步先把这些能力接成可使用、可交接的完整流程。下表保留实施顺序，Issue 保存实时状态；#11/#12 的最小入口已完成离线实现，不启动新的付费实验。

| 顺序 | 可独立验收的结果 | 任务 |
| --- | --- | --- |
| 收尾 | 补已有视频工具的真实 FFmpeg 集成验证，核对已实现能力的边界；不继续扩视频分析功能 | [#9](https://github.com/elexcfe/keel/issues/9)，沿用现有计划 |
| 近期主线 1 | 同一任务入口衔接复现、显式准入、同会话修复和独立验收，显示真实阶段、阻塞和共享预算 | [#11](https://github.com/elexcfe/keel/issues/11)，[实施方案](../plans/task-lifecycle.md) |
| 近期主线 2 | 接手者从统一交付入口找到环境恢复、复现演示、代码改动和前后验证，并能按材料重跑 | [#12](https://github.com/elexcfe/keel/issues/12)，[实施方案](../plans/task-handoff.md) |
| 后续完善 | 视频步骤导航、前后对照定位；确有需要再评估剪辑和字幕 | [#13](https://github.com/elexcfe/keel/issues/13) |
| 后续效果试验 | 动态时间/token 注入，检查报告及时性与质量是否改善 | 沿用 [#10](https://github.com/elexcfe/keel/issues/10) |
| 稳定交付后 | 先测同模型下 Keel 的增益，再比较主流 Agent；理解效果同时看时间与正确率 | 沿用 [#8](https://github.com/elexcfe/keel/issues/8) 和评测方案，不立即搭建评测平台 |

#11/#12 先共同确认任务/轮次/版本/报告引用约定，再分别实施。基础复现演示属于近期交付：它帮助人理解关键准备、操作顺序与结果，不只是抓瞬间异常。录屏随 Pi 的真实场景采集，环境版本和命令用可执行材料表达；不把自动剪辑、逐帧分析或独立播放器设为框架前置。

代码关系图、影响面分析、独立界面、多 Agent 适配、完整中断自动恢复等保留为后续方向；目前没有明确独立验收目标的设想不批量拆 Issue。交付约定、最小任务与 Markdown 入口已有离线实现，真实 Pi 运行和理解效果验证另行授权。

## 1. 第一版要交付什么

第一版处理 TypeScript / React 项目中复现步骤明确的前端行为 bug。用户提供项目和隔离的测试环境，Keel 整理材料，调用 Pi 修复，并交付代码修改、验证记录和改动说明。

四项职责分别承担以下工作：

| 职责 | 主要工作 |
| --- | --- |
| 流程与审核 | 管理任务进度，保存复现、定位和合入的确认，汇总结果 |
| 复现与验证 | Pi 生成检查、准备数据和采集证据；Keel 提供通用执行器与约束，外层独立验收 |
| 定位与修复上下文 | 整理问题、日志和相关代码，记录准备改什么以及实际改了什么 |
| 改动理解 | 说明行为变化、可能影响和需要额外审核的地方 |

早期计划考虑独立的流程控制服务、分别部署的复现与验证模块，以及包装 Claude Code 或 Codex CLI，并准备一个备用编码工具。之后曾确定采用 DeepSeek Harness 插件，现在由 Pi 接入方案替代。通用 MCP 接入（让不同工具交换任务材料的接口层）仍属后续设想，不要求第一版同时实现。

“修复上下文”就是修代码所需的背景和材料。环境运行、任务结果保存和代码关系分析作为公共能力。核心代码能够单独运行和测试；第一版通过任务材料和脚本接入 Pi，需要会话事件、工具限制或交互入口时再增加 Pi 扩展，暂不要求全部做成远程服务。

## 2. 复现与验证怎样实现

### 把描述变成可重复的检查

先从问题描述中整理预期行为、实际行为、触发步骤，再从日志中补充报错时间、错误位置和请求记录。缺少必要材料时明确指出，不靠猜测补全。

第一版使用 Playwright 编写浏览器检查。例如“备注未追加”应读取保存后的备注内容，不能只判断保存按钮点下去了。

每次运行前恢复相同的测试数据，并处理页面加载和异步操作的等待。先取得一次完整、可验收的目标失败记录；涉及偶发性或稳定性疑问时再安排必要重复，不无条件要求三次。环境启动失败、元素没加载或脚本本身报错，不能算成功复现。

展示检查步骤、预期结果和实际失败，让用户确认复现正确。确认后保存固定版本的脚本和检查条件，修复后原样重跑。长期可以把这些检查保留为项目测试，防止同类问题再次出现。

### 同时保存三类证据

| 证据 | 能回答什么 | 不能据此承诺什么 |
| --- | --- | --- |
| 同一检查从失败变为通过 | 目标问题在相同条件下是否解决 | 所有情形都已覆盖 |
| 项目已有测试和新增用例的结果 | 已检查功能是否出现回归，也就是原有功能被改坏 | 未测试的功能也没有问题 |
| 截图、视频、日志或请求记录 | 用户能否核对运行过程和实际结果 | 单凭界面看起来正常就认定修好 |

报告区分通过、失败和无法验证，逐项列出测试结果。已有失败和本次新增失败要分清；检查没运行不能写成通过。修复前后的代码版本、未提交修改、脚本、测试数据准备方式和运行记录，应能对应到同一个任务的具体轮次。

修复工具不能通过删除检查或放宽条件获得通过结果。如果检查有误，需要重新确认，并在修复前的代码上重新建立失败记录。结果由实际执行检查的程序生成。

### 定位、修改与再次检查

Pi 根据原问题、运行日志和相关代码定位原因；用户已有的线索可以作为输入，但不要求人先给出关键代码位置。Keel 保留材料与引用，可能原因必须附依据，不确定的部分要标明；额外人工定位帮助单独记录。

接入时要验证能否取得 AI 的修复计划、执行动作和代码修改。拿不到的信息明确记录为缺失，不能据此宣称已经检查了“实际改动是否符合计划”。

验证发现目标问题仍存在或出现回归后，保留当前结果，继续修改和检查；无法修好则说明失败原因。中断恢复要能知道哪一步完成、哪些检查需要重新运行。

## 3. 改动分析怎样逐步做

先做到文件和函数层面的清楚说明，再增加代码关系和影响分析。原构想中的五个步骤仍保留为技术方向，不要求在第一个 bug 上一次做完。

### 第一步：从代码行变化中找出实质变化

把新增函数、参数变化、逻辑修改与格式调整、引用路径变化分开。可以借助抽象语法树（AST，即按代码语法组织出的结构）比较修改前后，减少无关细节。

原稿提到 difftastic、GumTree 的比较思路，以及 tree-sitter 等解析工具，作为后续试验候选；尚未确定采用哪一种。

### 第二步：比较代码之间的关系

用节点表示模块、类和函数，用连线表示引用、调用、继承或数据传递。比较修改前后的关系，找出新增依赖、循环引用、跨越既定分层的调用，以及可能受影响范围的扩大。这就是原稿所说的“图 delta”，即两张关系图的差别。

先尝试文件依赖和函数调用关系。LSP（编辑器使用的语言服务协议）提供的定义和引用信息、madge 一类依赖分析工具，都可作为试验入口。数据具体怎样传递通常需要额外分析，不能假设现有工具已经给出完整答案。

第一版可以全量重算关系图；如果在真实项目上太慢，再研究只更新变化部分。动态调用和不同语言的差异会影响准确性，因此先限定一种技术栈。

### 第三步：对照准备做的事与实际改动

将修复前确认的目的、范围与实际代码变化对照。例如，只准备修登录，却还修改了计费模块，需要解释是否为必要联动。

有计划和实际记录才能做这个判断。多改一个文件不自动等于越界，也不能仅凭 AI 自述就认定符合约定。

### 第四步：找出可能影响的位置

沿引用和调用关系寻找哪些函数、页面或模块可能受影响，再结合测试覆盖记录，指出哪里已经验证、哪里还需检查。原稿称之为“影响面分析”。

代码关系说明的是潜在联系，不直接证明某个页面一定出错。无法分析的动态关系、缺失的测试覆盖都要标明。

### 第五步：把需要人注意的变化放在前面

让 AI 根据前面得到的代码事实和运行记录归纳说明，区分行为修改、结构整理、新功能和接口变化，再按审核需要排序。结构化信息能帮助减少猜测，但不能保证解释永远正确。

例如，报告可以这样展示：

- **优先检查：** 登录验证函数 `AuthService.verify()` 新增 `scope` 参数，四个调用位置中，`PaymentGuard` 可能漏改。
- **主要变化：** 登录逻辑迁移到 `TokenService`，与已确认的修复计划相符。
- **其他修改：** 十二处引用路径随文件移动调整，合并展示，仍可展开查看。

关系图突出新增、删除和需核对的连线。提示过多和漏掉重要变化都要通过真实案例检查，不能用统一阈值掩盖不确定性。

## 4. 运行环境与权限

复现、修复和验证在隔离的本地环境或测试站点中进行，不写生产数据。若需读取线上日志或配置，限定授权范围。

优先使用已有测试环境；需要可重复部署时再考虑容器化；涉及真实数据时再评估脱敏副本。插件本身不提供自动隔离，执行程序仍需明确允许访问的目录、服务和数据。

保存任务动作、代码版本、检查结果和人工确认，使人能追查结论的来源。原稿希望证据长期留档，具体保存期限和清理方式仍待确定，不直接承诺永久保存。

企业接入前，需要说明代码和数据会发送到哪里、存在哪里、如何加密、谁能访问，以及保留多久。这些是后续接入条件，不代表现在已经完成。

## 5. 开发顺序与完成标准

### 第一阶段：跑通一个真实 bug

从 Actual Budget 靶场选一个步骤明确的问题，先在修复前的代码版本上验证。Pi 负责具体场景、数据、修复和报告，Keel 提供通用约束和运行能力，外层负责确认及验收，不人工补写任务产物。完成以下工作：

- 准备隔离环境和测试数据，建立连续至少三次的目标失败记录。
- 接通最小流程入口，显示进度，保存复现和定位确认。
- 把材料交给 Pi 修改，检查命令行流程和扩展事件能提供哪些计划与执行记录。
- 原样重跑复现检查，运行相关测试，生成代码修改与证据报告；基本说明包含触发方式、原因依据、修改范围、验证结果和剩余风险。

**完成标准：** 同一检查在修改前稳定失败、修改后通过，相关回归无新增失败；在约定预算和人工参与边界内交齐代码、场景、证据与说明并通过独立验收。还要检查删改断言、测试没运行、环境启动失败时，不会误报交付成功。仅完成复现的任务不能算完整修复闭环。

原稿建议先挑五个 bug 做可行性试验。当前先跑通一个，再用其余问题验证能否复用；如果连一个都无法稳定复现，应查明原因或收窄问题类型，不直接扩大开发。

### 第二阶段：减少人工准备，支持自动纠错

加入自动整理日志和相关代码、中断恢复等能力；同一会话内读取检查失败并继续修改属于第一阶段的基本能力。用靶场中的其他 bug 检查哪些步骤可以复用，记录仍需人补充什么。

**完成标准：** 流程能用于其他真实问题；发现修复错误后能继续修改并重新验证，未修好的任务保留原因；中断后能继续推进，旧记录不会被覆盖。

### 第三阶段：补齐改动说明和影响分析

先交付文件、函数和行为层面的说明，再按前述五个步骤试验代码关系分析。用人为加入无关修改或遗漏调用位置的案例，检查报告能否指出值得注意的变化。

**完成标准：** 用户能找到“改了什么、为什么改、可能影响哪里、还要检查什么”，并查看相应代码和证据。记录错误提示和漏报，标明无法判断的范围。

### 后续：外部试点与扩展

保留原稿提出的 1–3 个外部团队试点设想，待内部流程可用且具备接入条件后安排。重点了解材料准备、确认步骤和报告是否好用，用真实 bug 调整复现方法与提示内容，并准备权限和数据说明。

**试点判断：** 团队能在真实项目中完成修复、愿意继续使用；遇到的失败有记录并能解释。是否扩大推广，根据任务结果和用户反馈决定，目前没有已完成试点的依据。

多语言、后端、只重算部分代码关系、更完整的数据传递分析、报错和问题跟踪工具集成，以及接入其他编程工具，均保留为后续方向。当前不为这些设想先建设通用平台。

## 6. 怎样评估效果

核心指标改为端到端交付率与人的理解效果，公式、人工介入和失败口径统一见 [评测方案](keel-evaluation.md)。验证流程完成率和自动纠错结果保留为辅助指标；“测试跑完”不能替代独立验收。理解效果同时看时间与准确率，未实际测量时不宣称节省时间。

开发阶段和评测阶段分开：先把上述第一阶段闭环做实，在少量真实问题上确认可复用性、保存成本和失败；第二、三开发阶段按闭环暴露的问题推进，不必为开始比较先做完全部 AST、关系图或独立界面。

| 评测阶段 | 要解决的问题 | 启动条件 |
| --- | --- | --- |
| A：修复闭环 | 能否交付一次独立验收通过的完整修复及可理解说明 | 当前优先；利用已授权工作积累记录，不新增付费调用 |
| B：同模型对照 | 同样模型和任务条件下，基础 Pi 与 Pi＋Keel 的差异是否来自流程机制 | 闭环可复用，输入/验收固定，预算、次数与任务集另行授权；理解效率采用固定材料与实际人员测量 |
| C：主流 Agent 对比 | 与 Codex 或 Claude Code 相比，交付率、人工介入、理解效果及成本有何取舍 | 同模型阶段结果可解释、流程稳定；先选一个外部工具，另行批准比较协议与预算 |

比较必须提供等价任务信息与交付要求，固定或披露环境、模型、版本、缓存和资源限制，独立验收并保留全部失败。单个演示成功不算总体胜出，不同模型的系统级结果不能直接归因于 Keel 架构。当前不启动新的付费实验、外部对照或人工计时；这些安排不是已实现能力或成绩。

原稿还有以下验收建议，保留其含义，避免丢失原来的考虑；**这些数字未经过校准，不是当前验收要求，也不是已经达到的成绩。**

| 早期建议 | 原本想验证什么 |
| --- | --- |
| 在二十个真实 bug 上，稳定复现率至少 60% | 流程能否处理不止少数精挑的案例 |
| 虚假修复数为零 | 避免宣布修好但实际仍有问题；有限样本不能保证以后永不出错 |
| 二十秒内理解改动，回答正确率至少 80% | 报告能否帮助人快速找对重点 |
| 人为加入偏离计划的修改，检出率至少 90% | 能否提醒超出约定的变化 |
| 至少一个试点团队持续使用四周 | 产品是否有持续使用价值 |
| 每周人工批准的带证据修复数、批准前耗时下降 | 是否在实际工作中被接受，审核负担是否减少 |

如需重新采用这些指标，先明确样本、测量方法和成本，再决定是否修改现有评测方案。

## 7. 资源安排与早期估算

需要覆盖三类工作：运行环境与验证、代码关系分析、流程与报告设计。原稿按一位全栈或基础设施工程师、一位程序分析工程师，以及半职产品设计估算；这不是已确认的人员配置。单人可以按阶段推进，优先完成真实修复，再做复杂分析。

主要成本包括 AI 编码和说明生成的调用费用、测试环境算力、结果存储，以及试点接入和支持。核心能力可独立测试，有助于减少对特定工具和整套环境的依赖。

原工期以 2026 年 7 月为起点，假设 1–2 人全职：前四周做可行性试验，第 4–12 周做复现与验证，第 12–20 周做改动分析，第 20–28 周试点；单人约需延长到 1.5–2 倍。该估算没有经过实际开发验证，且插件形式与阶段顺序已有调整，不能照旧推算交付日期。后续排期应依据实际投入和前一阶段结果。

## 8. 主要风险与应对

| 风险 | 应对安排 |
| --- | --- |
| 检查不充分，却报告修复成功 | 固定检查标准，保存修复前后证据，列出相关测试和未覆盖范围；无法验证就说明原因 |
| 真实问题难以稳定复现 | 先做小范围真实案例，区分缺数据、环境问题和偶发问题，必要时收窄范围 |
| 报告提示过多或漏掉关键影响 | 用真实反馈与人为加入的错误案例检查，重点展示行为变化，保留依据和不确定性 |
| 测试环境影响生产，或企业不接受数据处理方式 | 隔离执行、限制访问；接入前说明数据去向、权限和保存规则 |
| Pi 接口变化，或拿不到完整计划 | 固定经过验证的版本，集中维护启动与扩展入口；核心能力独立，缺失信息如实标注 |
| 代码关系分析太慢或不准确 | 先做文件和函数关系，观察真实耗时后再优化；不把不完整的关系当作完整影响范围 |
| 不断增加语言、场景和集成 | 以第一版范围和阶段结果约束扩展；改变方向时再决定 |
| 确认太多拖慢工作，或自动化让人无法掌握变化 | 保留现有关键确认，观察它们是否提供决策价值，清楚展示进度和修改范围 |
| 其他工具提供类似能力，Keel 的价值不明显 | 用实际任务和试点反馈判断收益，不依赖“其他工具做不到”的假设 |
