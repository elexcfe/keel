# Pi 环境准备与复现拆分实验

关联任务：[#6](https://github.com/elexcfe/keel/issues/6)。

状态：实验方案；已实现 single/split 运行监测、目录隔离、会话采集与描述性统计（[使用方式](../script_tool/make_bug/README.md#pi-运行监测默认开启)，Issue #7），已开始真实模型预实验，进展见 [运行监测计划](../plans/pi-run-monitoring.md)；尚无正式比较结论。问题是“两次独立任务是否比当前一次任务更有效”，不预设拆分获胜。本次比较只涉及环境准备和 Bug 复现，不涉及修复代码。

现有日常评测仍按 [评测方案](keel-evaluation.md) 执行；本文是用户单独提出的受控实验设计，不自动启动付费评测。

## 1. 比较什么

| 组别 | 任务组织 | 上下文与文件 |
| --- | --- | --- |
| A：当前方式 | 一次 Pi 会话完成环境准备和复现 | 启动时接收 TASK、SCENARIO、ENVIRONMENT、BUG；依赖清单按需读 |
| B：拆分方式 | B1 准备环境，退出；B2 新会话复现 | B1 接收环境任务及 BUG；B2 接收复现任务、场景要求、BUG 和环境交接文件，不接收 B1 聊天记录 |

A 保持当前生产提示原文，不为实验偷偷优化；B 使用同样的操作边界、环境规则、证据要求，只拆职责和交接。两组都能看到相同的 BUG 和代码，因为环境准备也需要知道是浏览器还是桌面任务。

B1 可以阅读启动说明、源码中的环境要求，安装包、浏览器和服务，检查项目能启动。不得修改业务代码，不得写目标 Bug 的复现测试、分析修复方案或交付 Bug 结论。若越界，保留这次结果并标注协议偏离，不悄悄剔除。

B2 不使用 --continue、--resume、fork 或会话摘要恢复；继续使用 B1 准备好的同一任务目录和依赖。它仍可诊断并补齐遗漏的环境，权限与 A 相同，补装算入 B 总成本，并记录为“交接后环境返工”。不能通过禁止 B2 修环境，人为制造拆分失败。

这项 A/B 测的是整套工作方式，包括分阶段提示、交接成本和上下文重置，不能单独证明“清空上下文”是收益原因。如果 B 明显更好，再另做 C：同样两阶段但沿用原会话，用来区分分阶段与新会话的影响；首轮不扩大到三组。

## 2. B1 怎样交接

B1 必须退出且留下以下内容，B2 从文件接手：

- `dependencies.json`：按用途分类的包、服务和工具，名称、版本、安装方式、安装者、路径、状态。
- `environment/handoff.json`：ready/blocked 状态、启动和停止命令、工作目录、必要环境变量名、端口、数据初始化/清理方法、服务配置路径、实际检查命令与日志、已知限制。不得包含凭据值或目标 Bug 的推断、断言、截图结论。
- `environment/check.sh`：只检查环境，不安装、不修代码、不判断 Bug。附实际运行结果；文件存在和 ready 声明不能证明可用。
- 必要的环境配置与日志。环境 smoke test 只能验证启动/访问能力，不应执行目标异常的触发序列。

B1 结束后执行器停止其启动的服务，保存工作区快照和依赖清单；B2 按交接说明重启。依赖文件保留，不重新安装。重启和交接时间计入 B 总耗时，不要求 A 做额外交接。这样测到的是实际可交接的两任务方案，结果中明确包含服务重启代价。

B1 提前失败仍必须保存阻塞和日志；有剩余预算则启动 B2，附缺失或失败的交接状态，允许自救。达到总上限则结束，算失败。B1 用完分段上限时终止进程组，保存部分记录后进入 B2，不把新会话当作额外预算。

## 3. 公平起点与预算

每个“Bug × 环境状态 × 重复编号”构成一对 A/B。两组分别从同一模板恢复，不能让 A 跑完后直接把其目录交给 B。

固定并记录：问题版本 SHA、BUG 原文、初始文件与锁文件摘要、Pi 精确版本、实际模型/提供商、推理档位、工具、模型设置和压缩配置。模型路由、回退或中途换模型均标注偏离；不把不同模型混在一起算收益。

隔离每组的项目、共享工具、包下载缓存、浏览器缓存、包管理器全局 store、服务数据、端口和会话目录。跨组不得读取报告、会话、场景或安装产物。预填缓存从同一只读模板复制，不能使用一份会被两组修改的目录。需要时用相同容器镜像并固定内部路径，避免不可迁移的绝对路径和软链接改变环境。

环境状态分开统计：

- 缺验证工具：项目包已准备，验证工具/浏览器或测试服务缺失；最贴近当前关注的问题。
- 环境已就绪：相同版本的项目包及验证工具均已准备，检查拆分是否反而增加交接开销。

首次下载全部项目依赖是额外场景，不在首轮混入；网络下载时延可能压过模型行为差异。模型端缓存无法完全控制时，记录 cacheRead/cacheWrite、随机 A/B 顺序并在相近时间运行，不能声称已完全消除缓存影响。

两组运行相同的 prepare_tools / prepare_deps 自动前置步骤，状态输入一致。实验总计时从前置脚本启动开始；脚本耗时单独保存。B1/B2 之间不再偷偷重复启动器预处理，交接后任何重装都记为 B 的开销。若脚本已经解决所有环境问题，这对实验测的是低环境负担下的表现，不能当成复杂环境恢复证据。

当前预实验每组总上限 1 小时（3600 秒），待有明显优化后再调整，A 使用完整额度；B1 最多使用 15 分钟或当前剩余时间（取较小者），B2 使用剩余总额度，B1 提前结束的时间可给 B2。准备脚本、进程启动、交接、重启及收尾均在总计时内。每组同等模型费用上限须在选定模型后填入实验配置；B1+B2 合计，不能每个会话各获一份额度。费用监控存在延迟时记录超额，不伪称精确硬限制。

不人工救场或给其中一组额外提示。超时、Agent 错误、安装失败、交接失败都进入分母。与方案无关的宿主机崩溃或提供商整体故障，按预先规定标为基础设施异常；完整保留原始记录，若重跑必须整对重跑，原始与补跑分别报告。

## 4. 样本与运行顺序

先做 2 个 Bug × 3 次配对重复，只用“缺验证工具”状态：6 对，A 共 6 个会话，B 共 12 个会话，总计 18 个会话。目的先验证流程、会话计费和交接能否测量，不拿这点样本证明普遍优越。

两个 Bug 建议一个现有 Actual 案例、一个具有不同环境要求的案例。每个案例都需由实验准备者事先确认在指定提交和数据下可稳定触发，判定标准在运行前冻结。当前 Actual #8351 目录已有业务改动及复现脚本，不能直接作为实验起点；从指定原始提交重建，并去掉历史报告、测试和修复线索。现有靶场条目仅是候选，不把文档写着“已确认”当作本次确认。

预实验后依据配对差异的波动和成功率决定正式样本量。可先规划至少 6 个 Bug × 3 次 × 2 种环境状态，即 36 对、108 个会话；这仍不是统计把握度保证。正式样本应覆盖不同项目/环境，全部来自同一项目则只能给该项目范围内的结论。

每对随机决定 A→B 或 B→A，整批保持大致平衡，记录随机种子；同一台机器串行运行，避免并发争抢 CPU、端口和下载带宽。重复是独立新会话和新工作区，不是同一会话继续三次。冻结正式提示、预算、指标和停止条件后不边看结果边修改；调整过的预实验不混入正式结果。

## 5. 什么叫更好

主指标：预算内交付“有效复现”的比例。有效复现须同时满足：

1. 实际触发与预定判据一致的目标异常，不能拿缺包、启动失败或选择器错误当 Bug。
2. 保存可核查的原始证据。界面问题需要可定位异常发生时刻的录屏或关键帧/事件组合；录屏缺失时按案例预定的替代证据标准判断。
3. 有可重跑的场景及数据恢复说明；独立验收者从交付快照重启，重跑两次均满足预定判据。首轮只选稳定案例；偶发案例需另定频次标准。
4. 没有修改业务实现、削弱已有断言或读取修复答案。越界交付主指标计失败，同时单独报告偏离类型。

Agent 宣称“已复现”、pi 退出码 0、run_scenario 执行完成，都不是验收成功。所有案例预先确认存在 Bug；因此“未复现”可以是诚实且合规的报告，但不算本实验的成功复现。

次指标：端到端耗时、全部模型费用、请求输入/输出/缓存 token、工具调用数、人工介入次数、第一次真实业务操作的时间、交接后环境返工次数、错误归因次数、证据完整性。B 的指标必须合计两个会话和交接，不能只拿 B2 与 A 比较。失败也花费了资源，不能从成本统计中删除。

自动指标先保存原始值。成功耗时只在配对双方都成功的子集比较，注明样本数；同时报告各组全部尝试成本以及“全部尝试费用÷有效复现数”（无成功时不可计算）。超时作为未成功/截尾记录，不把失败任务提前退出当作更快成功。

验收者只看匿名编号、冻结判据、交付代码及运行材料，先判结果再看会话和组别；有争议由第二人复核。可用固定提示的 AI 辅助初审，但最终关键争议要人工核查，不让执行 Pi 自己给自己评分。独立验收的时间和模型成本另记，两组使用相同验收流程。

## 6. Pi 会话记录怎么用

原始会话保存 JSONL；条目可能通过 id/parentId 形成树，不能当普通聊天文本按行数统计。会话内可包含消息、工具结果、压缩及用量条目，字段依 Pi 版本而异。先固定版本并用一次小型冒烟运行核实支持的参数和实际字段，再写解析器；已用本机 Pi 1.0.4 / deepseek-v4-pro 的最小调用确认 v3 会话和 usage 字段，并与统计器结果核对一致；中断保存与完整复现流程的真实调用仍待验证。参考 [官方会话格式](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/docs/session-format.md)。

执行器为每次实验显式设置独立 `--session-dir`，A、B1、B2 分别保存；不使用 --no-session，不复用已有文件。可另开 `--mode json --print` 保存过程事件与 stderr，但事件流和持久化会话是两份不同记录，不能把相同请求重复计费。所有会话由实验执行器收集在工作区外，B2 只拿交接文件，不把 B1 会话路径提供给它。是否实际保存成功须检查会话文件和 session id，不能只检查参数。

实验目标记录结构如下；当前工具已保存会话、阶段日志、交接与源码/依赖快照，场景证据仍由任务 result/ 保存，不自动复制到以下 evidence/：

```text
experiment/run-id/
  run.json                    # 分组、配对、版本、预算、起止时间、退出原因
  prompts/                    # 实际 TASK/SCENARIO/ENVIRONMENT/阶段提示和 BUG
  sessions/A/                 # A 运行时使用；B 运行改为 B1/、B2/
  events/                     # 事件流、stderr、脚本/进程起止记录
  handoff/                    # B1 结束时交接文件的不可变快照
  snapshots/                  # 初始、交接、结束时的代码/依赖摘要
  evidence/                   # 场景日志、视频、图片和每轮结果
  review.json                 # 匿名验收结果、依据、重跑结果
  metrics.json                # 从原始记录派生，可重新计算
```

必须额外保存实际命令行、环境变量白名单、全部提示词副本与摘要。不能假设任意 Pi 版本都在会话里记录完整系统提示；存在系统提示记录时再核对。配置和会话中可能出现凭据，分析副本要脱敏，不提交原始实验输出到 Git。

解析和人工标注约定：

| 要回答的问题 | 提取方法 | 限制 |
| --- | --- | --- |
| 总成本是否降低 | 汇总实际 assistant 请求用量，另计独立 usage、压缩/分支摘要调用；B1+B2 相加 | 以固定版本字段语义核对，避免双计；缺失记 unknown，不记 0；Pi 费用通常是估算，能取账单则核对 |
| 复现前花了多少环境工作 | 根据工具调用和结果标注 env / reproduce / report / mixed / unknown | 同一 shell 命令可能混合多步，不能凭 npm 等关键词就认定整段都是环境工作 |
| 是否重复准备工具 | 比对依赖路径、版本、安装命令、前后状态及错误上下文 | 失败后合理续装不是无效重复；同命令重复并不自动判错 |
| B2 是否丢失交接信息 | 检查其是否读交接、是否重新调查已交付信息、是否因缺漏返工 | 每个判定附 session id、entry id、toolCallId、文件/日志证据 |
| 上下文负担是否下降 | 每次请求输入量及缓存量、峰值、压缩次数，区分 B1/B2 | 输入量只是负担的代理指标，不等于模型注意力或因果证明 |
| 是否把环境失败误当 Bug | 对照错误、后续结论和独立验收 | 不能只依赖 Agent 自述或隐藏推理文本 |

成本统计包含所有实际发生的请求，即使后来切换分支或压缩；重建最终对话才沿有效分支处理。相同事件流和 session 条目应以请求/条目映射去重。时间使用外部执行器的单调时钟，事件时间用于定位，不用两条聊天消息时间差代替某个工具的耗时。无结果的工具调用标为中断/未知。缺少 token 字段时，只比较可核实的成本/时间，不用文件大小猜 token。

以上记录机制参考 [SessionManager 类型定义](https://github.com/badlogic/pi-mono/blob/main/packages/coding-agent/src/core/session-manager.ts) 和 [消息/用量类型](https://github.com/badlogic/pi-mono/blob/main/packages/ai/src/types.ts)；正式实现以锁定版本而非浮动 main 为准。

## 7. 如何下结论

先列每对的四种结果：都成功、仅 A 成功、仅 B 成功、都失败，再按环境状态和项目汇总。正式分析对同一 Bug 的重复做聚类或分层配对分析，不把同一 Bug 的多次运行当成许多独立项目。报告差值、置信区间和原始分母；成功率用配对方法，成本/耗时报告配对差值及区间。

正式实验前可预定实用判据：B 成功率不比 A 低超过 5 个百分点，同时端到端耗时或总费用至少降低 20%，另一项没有明显恶化且证据质量不降。若 B 成功率显著更高但成本更贵，应报告成本换成功率的取舍，不强行评成全面更好。这些是待预实验校准并冻结的产品门槛，不是已得到的结果。

成功率差异“不显著”不等于等效；区间太宽不能声称“不降低”。6 对预实验通常只能暴露流程问题。若证据不足，结论写“暂不能判断”，按预先样本计划继续或保留当前方案，不挑成功案例证明拆分优越。

最终输出应回答：在哪类环境下谁更好、成功率差多少、每次有效交付花多少总成本、会话证据支持什么机制、哪些差异仍不能解释。

## 8. 落地顺序

1. 固定真实 Pi/模型版本和案例，先确认 session 参数、消息、usage 和中断保存行为。只做格式验证，不先跑整批。
2. 在 `script_tool/make_bug` 增加独立实验执行器，保留当前 A 启动行为；从同一套规则生成 B1/B2 提示，显式记录所有差异。生产 run_pi.sh 暂不切换模式。
3. 实现隔离工作区、缓存恢复、预算/进程组终止、独立 session-dir、交接快照及会话分析器。测试双会话费用相加、缺失用量、重复事件、压缩/分支、中断及交接失败。
4. 选定模型后计算预实验费用上限，填入冻结配置；执行 6 对预实验并匿名验收，核对样本会话与派生指标。
5. 根据预实验确定正式样本量、门槛与提示版本，再开展正式实验。未得到结果前不改默认任务流程。

后续 Issue #7 已实现基础执行与监测；完整对照实验、热环境自动克隆、随机配对批量调度、语义标注和置信区间分析仍未实施。生产默认仍为 single，但 single/split 均自动监测；当前两个方案共同追加 MONITOR.md，正式对照须冻结此版本。
