## 1. 执行摘要

**Keel 是一个连接开发者线上环境的 AI 修复系统**：输入 bug 描述、项目文档和运行日志，Keel 自动复现问题、定位根因、调用现成编码 agent 生成修复，然后**在隔离环境中重跑复现用例，用运行时证据证明修复有效**，最后把改动翻译成一张人类可以在 20 秒内理解的架构影响图。

一句话对外定位：

> "别的 AI 给你一个 diff 让你自己担惊受怕；我们给你一个复现、一份运行时证据、一张架构影响图——你只需要点批准。"

**三个关键战略判断**（决定资源如何分配）：

| 输出 | 市场状态 | 我们的策略 |
|------|---------|-----------|
| 1. 改好的代码 | 红海，快速商品化趋近免费 | **不自研**，调用现成编码 agent |
| 2. 运行时验证证据 | 被低估的金矿，几乎无人闭环 | **重投入**，这是卖"信任" |
| 3. 可理解的改动说明 | 差异化独有 | **重投入**，这是卖"掌控" |

**MVP 切法**：单语言栈（TS/React）+ 单类 bug（有明确复现路径的前端行为 bug），90% 精力砸在复现引擎、验证闭环和理解报告三件事上。

**产品的心脏是复现引擎，不是改代码**——能复现才能验证，能验证才有信任，有信任才有产品。

## 2. 背景与问题定义

### 2.1 真实痛点

- AI 编程工具已经很强，但 **AI 改得太快，人跟不上**。
- 跟不上的**不是语法，而是改动的语义和影响面**。AI 一口气改 15 个文件，工程师肉眼看 diff 需要 20 分钟才能重建"它动了系统哪根筋"。
- 目标是把这 20 分钟压缩到 20 秒，并用图呈现。

### 2.2 痛点的另一半：信任缺失

现有 AI 编码工具的工作流是"生成完就祈祷"——它们不闭环：

- diff 交给人之后，验证责任完全落在人身上；
- 没有复现，就没有"修好了"的客观标准；
- 人被迫在"全盘细读"和"盲目信任"之间二选一，两者都不可持续。

### 2.3 已明确否掉的方向（避免走回头路）

早期曾设想加入**桌面视觉识别 + 语音识别**，"像人一样点着界面讲解代码"。经论证否掉，理由记录如下：

1. 界面↔代码的映射是**结构化、精确、免费**的（DOM + source map、React fiber、LSP 定义跳转/引用/调用图）。用视觉逆推一个本有确定答案的东西，精度更低、成本更高、还不稳定。
2. 程序员在安静专注场景下打字比说话快，语音属于炫技但没人用。
3. **保留的诉求**：给人讲解必须有**图像形式**——但这个图不是界面截图，而是"随 AI 改动实时变化的架构 diff 图"（见 §7.3）。

> ⚠️ 结论性约束：**不做视觉识别、不做语音**。"图像形式"由架构图满足。后续任何人重提此方向，先读本节。

## 3. 产品定位与价值主张

### 3.1 定位

一个连接开发者线上环境的 AI 系统：

```
吃 bug + 文档 + 日志 → 复现 → 定位 → 改代码 → 跑起来用运行时证据证明修好了
→ 再把改动翻译成人能快速理解的架构影响图
```

**卖的不是"帮你改代码"，而是"带证据、可理解的修复"。**

### 3.2 价值主张拆解

| 用户痛点 | Keel 的回答 | 对应能力 |
|---------|------------|---------|
| "这个 diff 真的修好了吗？" | 复现用例通过 + 回归套件不倒退 + 运行时截图/日志 | 验证闭环（§7.2） |
| "AI 到底动了系统哪根筋？" | 架构 delta 图 + 按注意力排序的变更面板 | 理解层（§7.3） |
| "AI 有没有干我没注意到的事？" | 声明意图 vs 实测图 delta 的偏离检测 | 意图对齐（§7.3 第 3 层） |
| "我该把注意力放在哪？" | blast radius 可达性分析 + 注意力排序 | 影响面分析（§7.3 第 4/5 层） |

### 3.3 人机关系：human-in-the-loop 是原则不是妥协

全自主修 bug 与初衷（帮人跟上 AI）矛盾——全自主把人踢出循环。Keel 在关键闸口让人确认：

1. "这样复现对吗？"（复现闸口）
2. "定位到这里，同意吗？"（定位闸口）
3. "这是证据和理解报告，批准合入吗？"（合入闸口）

**理解层恰好就是这些闸口的界面**——它是串起整个系统的骨架，而非附属品。

## 4. 目标用户与市场

### 4.1 目标用户画像

- **熟练工程师**（不是 vibe-coding 新手）。熟手也跟不上 AI 了。
- 产品要给的是"精确、影响面、注意力指引"，**不是"教你看懂代码"**。
- 早期切入：中小型团队中重度使用 AI 编码工具（Cursor / Claude Code / Copilot）、维护有真实用户的线上 Web 产品的工程师。

### 4.2 使用场景（MVP 阶段）

1. 用户报了一个前端行为 bug（"点了保存按钮没反应"）；
2. 工程师把 bug 描述 + 相关日志丢给 Keel，并授权 Keel 访问影子环境；
3. Keel 复现 → 定位 → 修复 → 验证 → 出理解报告；
4. 工程师在三个闸口各花几十秒确认，点批准合入。

### 4.3 市场判断

- AI 编码 agent 市场巨大且在快速增长，但**"验证与理解"层几乎空白**——现有玩家全部卷在代码生成上。
- 企业采购 AI 编码工具时的第一顾虑就是"AI 改的代码敢不敢上线"，Keel 正面回答这个问题。
- to B 售卖时，"每次修复附带一份证据报告"天然契合审计、合规和 code review 流程。

> 待办：正式立项前补一轮市场规模测算和 20 个目标用户访谈（见 §14）。

## 5. 竞争格局与护城河

### 5.1 竞争格局

| 玩家 | 他们做什么 | 与 Keel 的关系 |
|------|-----------|---------------|
| Cursor / Copilot / Claude Code | IDE 内代码生成 | **上游供应商而非对手**——Keel 调用它们生成修复；它们活在 IDE 里，够不着运行时 |
| Devin 及各类自主 agent | 端到端自主开发 | 部分重叠，但它们不闭环验证、无理解层，且全自主路线与企业信任需求相悖 |
| Sentry / Datadog 等可观测工具 | 报错聚合与告警 | 潜在集成入口（bug 摄入源），不做修复 |
| 静态分析 / 架构治理工具 | 规则扫描 | 不知道 AI"打算"做什么，做不了意图偏离检测 |

### 5.2 护城河（按坚固程度排序）

1. **意图对齐（最大壁垒）**：坐进 AI agent 的循环里，拿到它声明的意图，与实测图 delta 对齐。"AI 说只动登录，图 delta 却显示它顺手改了 BillingModule"——**这个'AI 干了你没注意到的事'的瞬间就是整个产品存在的理由**。静态工具做不到，因为它不知道 AI 本来打算做什么。
2. **运行时接入**：可远程连接的环境 + 运行日志，解锁复现与验证。IDE 型对手结构性地够不着。
3. **活的代码图 + 阈值模型**：增量图构建和"什么算架构级变化"的判断模型，是长期数据和调优的积累。

## 6. 产品总体设计

### 6.1 输入

1. 软件背景等文档；
2. 可远程连接的软件网站 + 服务器 + 运行日志（**杀手锏输入**，解锁复现与验证）;
3. 当前遇到的 bug。

### 6.2 输出

1. AI 改好的代码（商品，外采）；
2. 修改验证的证据包：复现用例通过记录 + 回归结果 + 截图/日志（金矿）；
3. 帮人快速理解 AI 行为的改动说明：架构 delta 图 + 注意力排序面板（差异点）。

### 6.3 端到端循环

```
1. Bug 摄入与复现   ← 心脏，最被低估，决定生死
2. 定位              ← 日志 + 代码图，缩小嫌疑
3. 生成修复          ← 调用现成编码 agent，不自研
4. 验证              ← 重跑复现，证明修好 + 回归不倒退
5. 理解层            ← 五层流水线，也是人工闸口的界面
```

第 1 步与第 4 步是同一件事的两端：**能复现才能验证**。

### 6.4 系统模块划分（初步）

```
┌─────────────────────────────────────────────────────┐
│                      Keel 控制面                      │
│   （任务编排 / 三个人工闸口 / 理解报告 UI / 审计日志）   │
├──────────┬──────────┬──────────┬──────────┬─────────┤
│ 复现引擎  │ 定位引擎  │ 修复适配层│ 验证引擎  │ 理解层   │
│ (§7.1)   │ 日志+代码 │ 包装现成  │ (§7.2)   │ 五层流水线│
│          │ 图检索    │ 编码agent │          │ (§7.3)   │
├──────────┴──────────┴──────────┴──────────┴─────────┤
│              活的代码图服务（AST/图构建、增量更新）     │
├─────────────────────────────────────────────────────┤
│         隔离执行环境（影子环境，不碰生产, §7.4）        │
└─────────────────────────────────────────────────────┘
```

## 7. 核心技术方案

### 7.1 复现引擎（心脏，最高优先级）

**问题定义**：怎么把"一个 bug 描述 + 日志 + 活环境"变成一个**能确定复现、之后又能用来验证**的 case？

MVP 阶段的技术路线（限定前端行为 bug）：

1. **输入解析**：从 bug 描述抽取预期行为、实际行为、触发路径线索；从日志抽取时间窗、错误堆栈、请求序列。
2. **复现脚本合成**：在影子环境中用浏览器自动化（Playwright 一类）合成操作序列，目标是产出一个**确定性失败**的可执行用例——"跑这个脚本，必然观察到 bug"。
3. **确定性收敛**：处理时序、异步、数据依赖导致的 flaky；复现用例必须连续 N 次稳定失败才算"复现成功"（N 待定，建议 ≥3）。
4. **复现闸口**：把复现过程录屏/截图给人确认"对，这就是那个 bug"。
5. **用例沉淀**：复现用例即验证用例，修复后原样重跑；长期看可沉淀为客户的回归资产。

**已知难点**：非确定性 bug（竞态、依赖外部服务状态）、需要特定数据状态才触发的 bug。MVP 明确排除这两类（见 §8.2 非目标）。

### 7.2 验证闭环（卖信任）

**三盆冷水之一必须正面回应：截图只证明"界面现在看起来对了"，不证明 bug 真修复、不证明无回归。** 单靠截图制造的是**虚假信任，比不验证更糟**。

因此验证证据分三级，缺一不可：

| 层级 | 证据 | 回答的问题 |
|------|------|-----------|
| 1 | 复现用例由"稳定失败"翻转为"稳定通过" | bug 真的修了吗 |
| 2 | 项目既有测试套件 + Keel 沉淀的回归用例不倒退 | 有没有修一个坏三个 |
| 3 | 运行时截图 / 日志 / 网络轨迹 | 给人看的直观佐证 |

证据包随修复一起产出，作为合入闸口的附件，并永久留档供审计。

### 7.3 理解层：五层流水线（卖掌控）

**核心思想：别让 LLM 看文本 diff 猜意思；先把改动结构化成图，再让 LLM 在结构化的图上做叙述和排序。** 这样准确、便宜、不幻觉。

1. **文本 diff → 结构化 diff（去噪）**
   解析成 AST，做 AST 级别 diff（difftastic / gumtree 思路）。把"改了 15 文件 800 行"压成"其实只发生了 6 件结构上的事"。

2. **结构化 diff → 图的 delta（这才是"架构变化"）**
   后台维护一张**活的代码图**：节点 = 模块/类/函数，边 = import/调用/数据流/继承。改动前后各算一次图，diff 两张图。架构变化 = 图的 delta：新增跨模块边、引入循环依赖、跨越分层边界、下游可达集变大等。**图的 delta 天生可画**，直接就是产品需要的图像形式。

3. **意图对齐（最大壁垒）**
   坐进 AI agent 的循环里（MCP 层包住 / 拦截它的 plan 和 tool calls），拿到它**声明的意图**。声明意图 × 实测图 delta，做两件事：
   - 生成人话摘要（"AI 重构了登录，改用 TokenService"）；
   - **偏离检测**（AI 说只动 A，实际还动了 B）。

4. **影响面 / blast radius**
   图上做可达性查询：改动函数被谁调用、哪些测试覆盖、连到哪个前端组件。输出"波及这 3 个组件和这条数据流"。

5. **注意力排序（secret sauce）**
   LLM 输入的是第 2/3/4 层已结构化的 delta，不是原始文本。分类（行为变更/重构/新功能/契约变更）+ 按"人需投入的注意力"排序。

**已知技术难点**（进 §11 风险表）：

- 图的**增量构建**：每次编辑重算全量调用图太贵；
- **数据流边**最值钱但 LSP 给不了，得自研，动态语言尤其难；
- 语言覆盖逐个啃，**别摊大饼**；
- "什么算架构级"的**阈值模型**直接决定面板太吵还是漏报——**这是生死线**。

### 7.4 权限与隔离（第一天就要设计）

**线上环境写权限 = 信任地狱。企业第一问就是安全和权限边界。**

设计原则：

1. **几乎一定在隔离/影子环境中复现和验证，不碰生产**；
2. 生产侧只需**只读**能力：日志拉取、环境配置读取；
3. 影子环境的构建路径（按实现成本排序）：客户已有 staging 环境接入 → 基于容器的环境克隆 → 数据脱敏快照；
4. 全链路审计日志：Keel 的每个动作可回放、可追责；
5. 代码与数据的边界、驻留、加密方案在第一份企业合同前必须成文。

### 7.5 修复适配层（明确不投入创新）

- 封装现成编码 agent（候选：Claude Code / Codex CLI 等，MVP 选一个主力 + 一个备胎）；
- 适配层职责仅限：组装上下文（定位结论 + 复现用例 + 相关代码图切片）→ 下发任务 → **拦截其声明的意图和 tool calls 供理解层使用** → 收取 diff；
- 意图拦截的产品形态（插件 / MCP 中间层 / 包一层 agent）是待决问题 #4，MVP 阶段先用"包一层"的最简形态验证，不做通用化。

## 8. MVP 定义

### 8.1 范围（做什么）

| 维度 | 选择 | 理由 |
|------|------|------|
| 语言栈 | **TypeScript / React** | 图信息最丰富；前端 bug 天然适合截图验证；白送"前端界面↔代码"映射 |
| bug 类型 | **有明确复现路径的前端行为 bug** | 复现引擎可行性最高的切口 |
| 修复生成 | 外采现成编码 agent | 红海不自研 |
| 精力分配 | **90% 砸在复现引擎 + 验证闭环 + 理解报告** | 战略判断的直接落地 |
| 运行形态 | 影子环境（容器化本地/staging 克隆） | 不碰生产 |

### 8.2 非目标（明确不做，防止范围蔓延）

- ❌ 后端 / 多语言支持（Python、Go 等留待 MVP 验证后）；
- ❌ 非确定性 bug（竞态、偶现）与强数据状态依赖的 bug；
- ❌ 自研代码生成模型；
- ❌ 视觉识别 / 语音交互（已否决，见 §2.3）；
- ❌ 生产环境写操作；
- ❌ 通用化的意图拦截中间层（MVP 用最简"包一层"形态）。

### 8.3 MVP 验收标准（草案）

在预先选定的 20 个真实前端行为 bug 样本上（来自试点项目）：

1. **复现率 ≥ 60%**：能产出确定性失败的复现用例；
2. **验证可信**：所有"已修复"结论均有三级证据包，零"虚假修复"（复现通过但实际没修）；
3. **理解报告 20 秒测试**：熟练工程师在 20 秒内正确回答"这次改动动了什么、该重点看哪"，正确率 ≥ 80%；
4. **偏离检测**：在人为构造的"AI 越界改动"注入测试中，检出率 ≥ 90%；
5. 至少 1 个外部试点团队完整走通端到端循环并愿意继续使用。

> 数字均为初始锚点，第一轮试点后校准。

## 9. 路线图与里程碑

> 时间以 2026-07 为 T0，节奏假设 1–2 名全职投入，供评审校准。

### Phase 0 — 技术侦察与拍板（T0 ~ T0+4 周）

目标：把 §14 前四个待决问题从"问题"变成"决定"。

- [ ] **Spike 1（复现引擎，最优先）**：手工挑 5 个真实前端 bug，人工+脚本混合方式验证"bug 描述 + 日志 → Playwright 确定性复现"链路的可行性与耗时；
- [ ] **Spike 2（验证闭环）**：定义证据包 schema，跑通"失败→修复→翻转通过 + 回归"最小示例；
- [ ] **Spike 3（图 delta）**：用现成工具（tree-sitter + LSP + madge 类）对一个真实 React 仓库构建代码图，验证 AST diff → 图 delta 的产出质量；
- [ ] **Spike 4（意图拦截）**：验证从选定编码 agent 拦截 plan / tool calls 的可行性；
- [ ] 隔离环境方案选型文档；
- [ ] 定名收敛：查 `Keel` 的 `.com`/`.dev` 域名与商标（备选 `keel.dev`、`getkeel`、`keelhq`；次选名 Verdict）。

**闸口**：复现 Spike 若证明"5 个里 1 个都复现不稳"，回炉重切 bug 类型，不进 Phase 1。

### Phase 1 — 复现引擎 + 验证闭环（T0+4 ~ T0+12 周）

- [ ] 复现引擎 v0：bug 描述 + 日志 → 影子环境中确定性失败用例，含复现闸口 UI（可以极简）；
- [ ] 影子环境 v0：容器化拉起目标 React 应用；
- [ ] 验证引擎 v0：三级证据包自动产出；
- [ ] 修复适配层 v0：包装一个现成编码 agent 跑通"定位→修复→验证翻转"。

**里程碑 M1**：在内部样本上端到端走通"bug 进 → 证据包出"（可以没有理解层）。

### Phase 2 — 理解层（T0+12 ~ T0+20 周）

- [ ] 活的代码图 v0（先全量重算，增量优化延后）；
- [ ] 五层流水线 v0：AST diff → 图 delta → 意图对齐 → blast radius → 注意力排序面板；
- [ ] 偏离检测 + 注入测试集；
- [ ] 三个人工闸口串成完整产品流。

**里程碑 M2**：内部完成"20 秒理解测试"，阈值模型第一版（吵/漏报可接受）。

### Phase 3 — 试点与打磨（T0+20 ~ T0+28 周）

- [ ] 1–3 个外部试点团队接入真实项目；
- [ ] 用真实 bug 流量校准复现率、阈值模型、证据包形态；
- [ ] 安全与权限文档（面向企业问询）；
- [ ] 依据 §8.3 验收标准评估 MVP。

**里程碑 M3（MVP 达成判定）**：验收标准全部达标 → 进入商业化规划；未达标 → 依据数据决定调整切口或路线。

### Phase 4 — 扩展（M3 之后，仅列方向）

- 语言栈扩展（下一个候选栈按试点需求定）；
- 增量图构建、数据流边自研；
- bug 摄入源集成（Sentry / issue tracker）；
- 意图拦截通用化（MCP 中间层产品形态）。

## 11. 风险管理

| # | 风险 | 等级 | 应对 |
|---|------|------|------|
| R1 | **虚假信任**：证据体系不扎实，"看起来修好了"实际没修，砸掉产品唯一卖点 | 🔴 致命 | 三级证据缺一不可；宁可报"无法验证"也不出弱证据；零虚假修复作为硬验收线 |
| R2 | **复现引擎可行性不足**：真实 bug 的复现率远低于预期 | 🔴 致命 | Phase 0 Spike 先行；不达标就收窄 bug 类型而不是硬上；复现闸口让人兜底 |
| R3 | **阈值模型失准**：理解面板太吵（人忽略）或漏报（人失去信任），生死线 | 🔴 高 | 试点期人工标注反馈回路；宁漏勿吵先做保守版；分级呈现（🔴🟡⚪）缓冲 |
| R4 | **企业安全顾虑**：线上环境接入吓跑客户 | 🟠 高 | 影子环境 + 生产只读为第一天的架构约束；安全文档先于销售动作 |
| R5 | **意图拦截依赖上游**：编码 agent 接口变动 / 不开放 plan | 🟠 中 | 适配层隔离变化；主力+备胎双 agent；MCP 生态标准化是长期利好 |
| R6 | **范围蔓延**：多语言、后端、通用化诱惑 | 🟠 中 | §8.2 非目标清单；每次加范围走正式评审 |
| R7 | **上游对手补齐验证能力** | 🟡 中 | 押注运行时接入 + 意图对齐两个结构性壁垒；加快试点占位 |
| R8 | **图构建性能**：全量重算太贵拖垮体验 | 🟡 中 | MVP 容忍分钟级延迟；增量构建列为 Phase 4 攻坚 |
| R9 | **全自主倾向漂移**：迭代中不知不觉把人挤出循环，背离初衷 | 🟡 低 | 三闸口为产品不变量写入设计原则 |

## 12. 商业化初探

> 本节为方向性草案，MVP 验证前不做承诺。

- **计费锚点**：按"带证据的修复"计费（per verified fix），而非按席位——与价值主张一致，且天然区隔于按席位卖的编码工具；
- **to B 叙事**："AI 改的代码敢上线"——证据包对接 code review、审计、合规流程；
- **落地路径**：试点团队 → 设计合作伙伴（design partner）→ 中小团队自助 → 企业版（私有化影子环境、SSO、审计）；
- **与编码工具的关系**：共生不替代——"你已经在用 Cursor？很好，Keel 让你敢批准它的改动。"

## 15. 附录

### 15.1 命名决议记录

- 定位两根主线：**掌控**（帮人跟上/稳住 AI）vs **证据**（卖验证/可信）。
- **Keel（龙骨）**——首选。船高速航行时让它稳、不偏航；AI 是飞奔的帆，Keel 是让人稳住方向的龙骨。能装下修复+验证+理解全部三个输出，延展性好。
- **Verdict（裁决）**——次选。锋利、专业、to B 搭，但易被理解成纯验证工具，天花板略低。
- 其他候选：Tether、Helm（掌控向）；Attest、Vouch（证据向）；Lucid（理解向，但 AI 圈已用烂）。
- 待办：定名前查 `.com`/`.dev` 域名和商标（常见词，可能需前后缀：`keel.dev`、`getkeel`、`keelhq`）。

### 15.2 术语表

| 术语 | 含义 |
|------|------|
| 复现引擎 | 把 bug 描述 + 日志 + 活环境转化为确定性失败用例的子系统；产品的心脏 |
| 证据包 | 复现翻转 + 回归结果 + 运行时佐证三级证据的集合 |
| 活的代码图 | 后台持续维护的代码结构图：节点=模块/类/函数，边=import/调用/数据流/继承 |
| 图 delta | 改动前后两张代码图的差异；"架构变化"的形式化定义 |
| 意图对齐 | AI 声明意图与实测图 delta 的比对；偏离检测的基础 |
| blast radius | 改动的影响面：图上可达性查询得出的波及范围 |
| 阈值模型 | 判断"什么算架构级变化、什么值得人注意"的模型；决定面板吵/漏 |
| 三闸口 | 复现闸口、定位闸口、合入闸口——human-in-the-loop 的落点 |
| 影子环境 | 与生产隔离的复现/验证执行环境 |
