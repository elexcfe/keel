# Keel 产品说明

Keel 的目标是加快人与 AI 的协作效率：减少反复解释、等待和返工，让人容易理解改动、判断结果、推进工作。当前围绕现有编码 Agent，组织 Web Bug 的复现、修复和评审，交付可审核的代码与证据，并验证能否减少工程师反复检查和纠正的时间。

Keel 聚焦两个可验证的亮点：

| 亮点 | 对用户的价值 | 要用什么证明 |
| --- | --- | --- |
| 可靠交付 | 在限定预算内完成有效复现和正确修复，减少错误宣布成功 | 独立确认复现对应原问题、修复通过必要回归；同时记录错误放行、失败、人工介入、费用和耗时 |
| 减少人工核查与返工 | 更快看清触发方式、原因、改动依据、影响范围和未验证部分，作出正确审核判断 | 实际审核者的用时与判断正确率，以及包含模型、人工核查、抽检和重试的完整交付成本 |

这些是待证明的产品目标，不是已取得的指标。端到端交付止于可审核的修复包，不意味着自动合并或部署；文件齐全、Agent 正常退出、检查全部执行，也不等于修复通过验收。统计定义和分阶段验证以 [评测方案](keel-evaluation.md) 为准。

本文说明产品目标、使用方式和关键取舍。当前采用 Pi 作为运行与编码主体，Keel 提供执行约束、场景运行、记录和交付核对。已有 Actual 案例在外层反馈后完成修复与独立验收；统一命令行与 Markdown 交付入口主要经过离线验证。它们证明了部分流程可行，尚未证明无人干预的完整闭环，也未证明相对直接使用 Pi 的收益。

下一项任务是[复现评审回放原型](../plans/reproduction-review-replay.md)：先验证独立评审 Agent 能否发现复现与断言的问题，再决定是否接入自动反馈。当前只有规划，不能写成已实现多 Agent 协作或已经降本。

## 1. 给谁用，解决什么问题

先面向中小型团队中经常使用 AI 编程工具、维护 Web 产品的工程师。他们能读懂代码，但仍要花精力核对 AI 的工作：背景有没有理解对，测试有没有真正运行，修改是否影响其他功能。

例如，AI 一次改了 15 个文件，开发者需要重新梳理这些修改之间的关系，才能判断它是在修登录问题，还是连支付逻辑也改了。问题在于理解整次改动的目的和影响，而不只是读懂某一行代码。

Keel 希望减少三类负担：

- **反复解释和准备。** 把问题描述、项目资料、日志和相关代码整理好，后续步骤能够继续使用。
- **反复催促和返工。** 主动运行检查，在交付前发现修复仍有问题，并继续纠正。
- **审核时重新摸索。** 说明改了什么、证据是什么、可能影响哪里，把需要人判断的地方讲清楚。

是否减少负担，需要记录真实任务中的审核、纠正和等待时间；不使用没有测量依据的效率提升数字作为目标结果。

## 2. 用户提供什么，拿到什么

用户提供 bug 描述、项目代码和可用的测试环境，按需要补充项目文档、日志、预期行为和测试数据。仅有一句报错通常不足以复现；Keel 应指出缺少什么，逐步减少需要人手工整理的材料。

可运行的环境和日志很重要，因为它们让 Keel 能观察问题、重跑同一检查，而不只根据代码猜测结果。早期设想直接连接网站和服务器；当前优先使用隔离的本地环境或已有测试站点。需要线上资料时，只在授权范围内读取，不修改生产数据。

一次修复应交付三样东西：

| 结果 | 用户用它判断什么 |
| --- | --- |
| 代码修改 | 具体改了哪里，是否接受这次修改 |
| 验证记录 | 原问题是否解决，相关测试结果怎样，哪些部分还没检查 |
| 改动说明 | 为什么这样改，可能影响哪里，哪里需要重点审核 |

验证记录包括修复前后的同一检查、相关测试结果，以及截图、日志或请求记录等佐证。图形报告和关系图仅在能帮助理解时补充，用于展示模块、函数或页面之间的联系；它们不是强制交付，也不能代替代码和测试结果。

交付还需要让接手者知道怎样准备环境、怎样触发问题。已有最小交付入口关联三部分：可执行的环境准备与检查材料、真实复现演示、修复说明与验证结果，真实接手效果仍待测量。视频展示必要准备、页面状态、操作顺序和异常/修复后结果，帮助理解复杂流程；准确依赖版本、命令和测试数据由清单与脚本提供，不要求接手者从录像抄命令。基础演示随 Pi 的真实场景产出，静态问题可用截图，非界面问题使用日志、请求和数据；不强制每个任务录屏，也不要求精美剪辑或逐帧分析。

## 3. 一次修复怎样进行

以“保存交易后，备注没有追加规则要求的文字”为例：

1. 用户提交问题、项目和测试环境，Keel 保存任务材料。
2. Pi 编写可重复运行的场景、准备隔离数据并采集证据；Keel 执行和记录，外层确认观察与原问题一致，选定参考运行。
3. Pi 根据问题、日志和代码说明可能原因与修改范围，必要时请用户确认范围。
4. Pi 在一个修复会话内修改代码，通过 Keel 的场景执行器原样检查，并根据结果继续纠错。
5. Pi 更新阶段报告，交齐环境重跑材料、复现演示、原因与改动说明；Keel 核对最终代码、检查和引用，外层独立验收，保留失败与未验证部分。
6. 用户查看可审核的修复包，决定是否合入；Keel 不自动合并。

报告应先说结论，再给依据。例如：“备注现在能正确追加，原来的检查已通过。相关规则测试通过；其他页面尚未检查。这次还调整了规则执行顺序，需要重点审核其他规则是否受影响。”

复现准入、最终独立验收和用户决定是否合入需要明确记录；修改范围存在重要分歧时再确认。确认内容应帮助人作决定，避免让人重复核对已经提供的信息。理解说明贯穿这些步骤，而不只是最后附一段摘要。当前已有统一命令行任务入口和 Markdown 交付入口，复用各段工具并经离线验证；阶段启动、准入和最终验收仍由外层显式操作，不能把完整流程说成已全自动运行或真实效果已验证。

后续拟采用“执行者＋评审者”两个角色。执行者仍负责产出场景、修复和报告；评审者在复现准入和最终交付等关键关口核对目标行为、断言与证据，普通程序先处理文件缺失、版本不一致等机械检查。首个回放原型只读取冻结材料并给出建议，建议单独保存，不修改 Pi 产物或原始证据，不自动准入、不触发修复或重试。更强模型能否胜任评审、能否减少人工工作，需要测量后决定。

## 4. 为什么重点做验证和改动理解

**先复现，才有一致的修复标准。** 如果不知道怎样让问题出现，就难以判断一次修改是否解决了它。复现步骤还可以成为后续防止同类问题再次出现的测试。因此，先投入复现和验证，再逐步扩大自动定位与分析能力。

**界面证据需要与检查结果对应。** 瞬间闪烁或消失可以原始视频为主要证据，由 Pi 明确视频位置、异常时间段和观察点，不强求截图截中瞬间。界面看起来正常，不代表保存的数据正确，也不代表其他功能没有受影响。Keel 必须同时提供目标问题的检查结果和相关测试结果。环境没启动、测试没运行、检查范围不足，都要如实说明。

**说明要建立在代码和执行记录上。** 先分析实际改动与代码关系，再让 AI 归纳和排序；对照修复前的计划，提示可能超出约定的变化。例如，原本只修登录，却同时改了计费模块，就需要解释两者的关系。多改一个文件不自动等于越界。

改动报告可以把“登录验证函数增加了参数，有一个调用位置可能漏改”放在前面，把单纯的引用路径调整合并到后面。这样，用户先看到可能影响行为的变化，仍能查看全部修改。复杂关系分析按需后置，当前先保证解释能引用实际代码与运行证据。

两个亮点要一起成立：交付正确但难以审核，仍会增加人的负担；说明清楚却没有可靠验证，也不能算成功交付。基本的原因、改动和证据说明从第一个闭环就要提供，不等复杂关系图完成后再做。

代码生成使用现成工具，Keel 的主要投入放在复现、验证、评审和解释上。先查清现有失败原因与人工负担，再决定需要增加哪些机制。

## 5. 第一版范围与取舍

| 选择 | 理由和边界 |
| --- | --- |
| TypeScript / React 项目 | 从一种技术栈开始，便于把浏览器行为与相关代码联系起来，避免同时解决多种语言的分析问题 |
| 有明确步骤的前端行为 bug | 可以检查文字、数值和交互结果，较容易建立修复前后的对照 |
| Pi | 复用仓库已有的运行与复现路径，先验证流程；这是开发成本选择，不是已经证明优于 Codex 或 Claude Code |
| 隔离的测试环境 | 允许反复准备数据、运行脚本和修改代码，不影响真实用户 |
| 记录并逐步减少人工介入 | 现有流程依赖外层复现审核，先测量评审建议能否帮助人；从原始 Issue 评价完整收益时，人工补充和救援必须记录，不能算作自主完成 |

第一版暂不处理后端、多语言、偶发竞态、依赖不可控外部服务或难以重建数据状态的问题。需要固定测试数据的简单问题仍可纳入，例如为备注规则准备几笔测试交易。

早期讨论过桌面视觉识别和语音讲解，目前不做。对于能从网页元素、组件信息或代码引用关系中找到的线索，优先直接读取这些资料；不增加一套通过截图猜代码位置的流程。语音、复杂关系图和视频加工都后置，只有实际审核需要时再投入。

这些取舍用于控制第一版范围。后续是否增加能力，要根据真实任务的需要决定。

Pi 和 Keel 扩展要固定经过检查的版本，升级后重新运行代表性任务。核心验证工具继续保持可通过命令行独立调用；后续若用户主要使用 Codex 或 Claude Code，再按需求提供 Skill 入口，让 CI 复用同一套检查。当前未实现这些适配，也没有独立客户端或通用多 Agent 平台的优先需求。

## 6. 风险与仍需验证的产品判断

首先要防止“看起来很可信，实际没有检查清楚”。测试通过只说明已检查范围内没有发现问题，不能承诺整个项目绝对正确。两个 Agent 一致认可也可能来自同一个错误假设，不能作为评测真值。评审 Agent 的漏判与误判要由独立标准检查；后续即使允许自动通过，也需要按预先规定的规则核查双方都认可的结果，而不只看有分歧的任务。

其次，报告如果提醒过多，用户会忽略它；遗漏重要影响也会损害信任。需要用真实任务逐步调整提示内容，并标明无法判断的部分。用户是否愿意提供测试环境、材料准备是否太费力、评审是否减少纠正和返工，也是试点要回答的问题。工程上的风险和应对安排放在项目计划中。

Keel 与其他工具的关系，按协作需要考虑：

- 编程工具可以提供代码修改能力，也可能与 Keel 的部分能力重叠。
- 报错与日志工具可以成为问题来源；问题跟踪系统可以提供任务入口。
- 代码分析工具可以提供引用和依赖关系，Keel 再结合任务目的和执行记录解释变化。

Skill 可以携带脚本，CI 也可以执行检查和保存证据，因此 Keel 的工作流并非这些方案无法承载的能力。值得积累的是可复用的验证工具、来源清楚的材料、可靠的运行记录和评测结果；独立维护代码不等于需要让用户采用独立产品。是否有持续使用价值，要由交付质量与完整成本证明。


## 7. 怎样逐步证明项目价值

后续按以下顺序推进，不以角色数量或流程复杂度作为进展：

1. **复现评审回放原型。** 用来源清楚的冻结材料，分别检查有效复现、断言不足和证据不足等情况；开发样例与未用于调提示的评估样例分开。输出建议、证据引用和错误分析，评测答案不传给评审 Agent，不代写 Pi 产物。先回答能发现哪些问题、还会漏掉或误判什么。
2. **有限自动反馈。** 只有回放结果支持继续投入后，才把建议接入“退回 Pi—重新执行—再次评审”，限制次数与总预算；保留原始材料、修改版本与人工介入记录，验证是否减少返工。
3. **原始 Issue 完整对照。** 两组从相同 Issue、故障版本和基础环境出发，不提供仅给一组的答案、场景或断言。相同执行模型与预定预算下比较直接使用 Pi 和 Pi＋Keel；运行中不临时救援，结束后由独立标准判卷。仍需外层准入的环节必须计入，不能偷偷代劳后记成自主完成。
4. **按需求接入 Skill／CI。** 流程收益有依据、用户有需求后，再提供薄入口和共享检查，不提前建设独立客户端或多套 Agent 适配。

完整收益需同时看正确交付、错误放行、人工核查时间和总成本。总成本包含失败、退回重做、模型调用、工具执行、人工审核与抽检；不能只比较成功样本，或把额外评审当作免费帮助。引入强模型后，还要与强模型单独完成任务的方案比较，避免把更高模型能力误记成编排收益。回放校准与实验统一判卷的准备成本单列，实际使用仍需要的审核和维护纳入落地成本。

理解效果通过匿名材料、固定问题和实际人员的用时／正确率测量；组件回放有效、自动反馈有效、整体降本是不同结论。没有实际测量就不声称节省了审核时间，没有独立验收就不把自测全绿记为成功。具体准入、人工介入、失败统计与公平比较规则见[评测方案](keel-evaluation.md)，下一项任务的范围与检查方法见[复现评审回放计划](../plans/reproduction-review-replay.md)。

对外演示或面试使用真实失败、工程改进和测量结果说明价值。少数案例胜出不能证明普遍更强；若单个强模型或更简单的流程更划算，应保留有用工具并精简编排。本次仅更新方向与计划，不启动代码实现或新的付费实验。
